## 缺陷 1 🔴 报告证据区是空壳（子智能体已修，主控实测确认）

**原状**（`#/report/9cfbcb3…` 实测）：

```
<span class="src-line__tid">T1</span>
<span class="src-line__desc">对应这次取数的任务描述与工具，见正文角标与本行的编号</span>
```

"见本行的编号"是自我循环，等于没说。根因：`FinalReport.citations` 实测就是裸编号数组 `["T1","T2"]`，归档链路里没有工具明细。

**现状（有明细时，实测原文）**：

```
T1 按地区分组汇总销售额 · 返回 6 行 · 列：地区、销售额_sum ·
这一次工具调用耗时 2 毫秒（单次调用的时间，不是六阶段任何一个阶段的进度） ·
正文出现在：分析口径与覆盖范围、销售额合计：华南领先、哪个地区赚钱能力最强 · group_aggregate
```

`elapsed_ms` 是 `schemas_tool.py:74` 的真实字段，这里**只用于单次工具调用**，并且文案自己就把"这不是阶段进度"讲死了——没有违反 `00-brief` 2.2-3 / D-6。

**现状（无明细时，实测原文）**：`T1 归档只保存了编号 T1，工具与行数要等该次运行还在服务端时才读得到。正文出现在：…`

守卫：`test_evidence_rows_carry_real_backend_fields`，并断言那句圆话在三个文件里都不许回潮。

## 缺陷 2 🟡 假可点（子智能体已修）

态势带结论里的 `sup.cite` 原本没有 `tabindex`/`role`，`jumpToEvidence` 向上找不到 `.src-line` 就静默 no-op；而挂可访问属性的选择器只覆盖 `.doc__cites`，报告文档内另有 6 个角标漏在外。

**现状（实测）**：报告文档内 `sup.cite` 全部 `tabindex=0` + `role=link`；点击 `T1` 后 `.src-line[data-task-id="T1"]` 出现 `is-jump`。态势带内的引用标记改为**静态**，不再伪装可点。
守卫：`test_doc_cites_are_focusable_and_posture_marks_are_static`。

## 缺陷 3 🟡 对已归档运行说"尚未开始分析"（子智能体已修）

**现状（实测原文，`#/runs/9cfbcb3…`）**：

> 这条运行已经结束并归档。阶段级进度只在运行期间由服务端的状态接口提供，归档记录里不保存阶段序号，**所以上面六段阶梯对这条深链一段都不点亮 —— 那是"这一条没有可查的阶段数据"，不是"这条运行没有跑过"**。
> 任务编号 … · 状态 成功 · 结束于 2026-10-17 01:46:38 ｜ 已用时 6.3 秒 ｜ 【查看报告】

三态齐备：① 正在跑（真实 `step_index`）② 已归档（上面这段 + 真入口）③ 查不到（"后端对『不是你的记录』和『记录不存在』回的是同一个 404，所以这里无法区分是哪一种；页面不会把你领到别的记录上去"——与 `DECISIONS.md` §8.3.1 禁 fallback 复活一致）。
守卫：`test_archived_run_deep_link_is_honest_about_ladder`、`test_paint_steps_writes_the_css_state_hook`。

## 缺陷 4 🔴（主控新发现并修复）归档报告的深链根本打不开

子智能体三条修完后，主控**重启后端**（注册表清空）再走一遍，发现：

```
工作流不存在（原值码：NOT_FOUND）
这个 workflow_id 没有登记过，或者它不属于当前登录用户。
工作流状态存在服务进程的内存里，服务重启后全部丢失。
```

点自己那条**已经成功、就在归档里**的分析，看到的是"不存在"。根因：`loadReport`（`app.js:4136`）只调接口 7，没有归档回退。

这不是新引入的 bug，而是老限制被方案 01 **放大成主路径故障**——「查看报告」现在是首屏态势带和历史记录的一等入口。子智能体那 3 条守卫都覆盖不到它，因为它们测的是"能不能打开"，而它在活注册表面前一直是绿的。**必须重启进程才会暴露**，这也是本项目里"报告跑通=代码写完"式验收会漏掉的典型。

修复（`app.js:4136` 附近）：先问接口 7（活运行才有工具明细），答不到才回退接口 10 归档，并带 `fromArchive: true`；两条都不交出内容时报的是**归档**的错误而不是把注册表 404 当唯一事实。正文顶部新增来源说明：

> 这份报告读自归档库。服务进程已经不再有那次运行的内存状态，所以阶段进度与工具调用的逐条明细不在这里显示；下面的数字仍可按编号逐条对照。

守卫：`test_report_deep_link_falls_back_to_the_archive`（钉调用顺序、`fromArchive` 分支、`API.report(` 仍恰好一处）。

## 未解决 / 遗留

- **`.btn--primary` 色值未改成方案 01 的 navy**：被 `test_frontend.py:547` 钉住，且同屏会出现两种主按钮色。已记为已知偏差（`06` D-1 附注、`COMMAND_CENTER_MIGRATION.md` 偏差表）。
- **两套墨阶并存**：正文/标题保持存量暖阶 `--n-*`，新组件用冷阶 `--ds-ink-*`。改全站墨阶的风险远大于收益。
- **视觉判断没有做过**：本机内嵌浏览器 `window.innerWidth=0`，所有 `matchMedia` 都判命中。主控一度据此把"侧栏会话时长 `visibility:hidden`"当成缺陷，实为**零尺寸视口把侧栏判成关闭抽屉态的环境假象**，已撤回。像素级效果必须由用户在真浏览器里看。
- **开发库脏数据**：`data/db/app.db` 的 `workflow_history` 有 680 行，含明显的测试合成行（`aaaaaaaa…`、`0123456789abcdef…`）。它们会让首屏态势带/历史出现非用户真实的记录。属数据卫生问题，不是 UI 缺陷，未擅自清理。
- `data/auth.db` 是一个 **0 字节的干扰文件**（真库是 `data/db/auth.db`）。主控据此误判过一次"账号库为空"。
