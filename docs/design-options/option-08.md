# 方案 08：高管决策简报 / Decision Room

> 上游依据：`docs/design-options/00-brief-and-matrix.md`。对应 Demo：`design-options/option-08/index.html`。
> 坐标：单页纵向滚动 + 右侧锚点进度条，**无导航栏**；首屏 = 关键发现卡（≤5 张）+ 取舍对比；密度低；数据主角 = 结论卡 + 对比矩阵；亮色；立场"先给答案，再给理由，最后给证据"。

---

## 1. 设计名称

**高管决策简报 / Decision Room**。一屏之内按"答案 → 取舍 → 理由 → 行动 → 证据"五层纵向展开，像董事会桌上的一页纸，不像工作台，也不像长文档。

## 2. 核心设计理念

这套方案表达的是：**决策者的阅读顺序就是产品的输出顺序**。传统分析平台把"数据集、任务、运行"放在最前，是因为建没设平台的人也是分析师；但真正为结论买单的人只关心三件事——答案是什么、代价是什么、凭什么信。因此本方案取消导航栏与功能分区，登录成功后直接落地一份"简报"：首屏是不超过 5 张的结论卡，每张卡一句话给出可被直接引用的决策建议；紧随其后是取舍对比矩阵，把"选 A 放弃 B"的成本摆平在同一张表里；再往下才是推理段落、报告给出的行动建议、以及每条结论锚回的真实工具证据（`cites` 角标 T1/T2…）。右侧锚点进度条是全页面唯一的位置感来源，它替代了导航栏的职责——你不需要去别的页面，你只需要决定读到哪一层为止。低密度不是空，而是让每一个数字都有资格占据视线。

## 3. 视觉关键词

纸感、墨色、结论卡栈、留白分层、锚点进度、克制的铜色强调。

## 4. 色彩体系

| 角色 | hex | 用途 |
| --- | --- | --- |
| 背景色 | `#F7F5F0` | 纸面底色（亮色主题，全站唯一底色） |
| 表面色 | `#FFFFFF` | 结论卡 / 矩阵 / 登录卡 / 报告容器 |
| 主色（决策绿） | `#14504A`（软底 `#E3EDEA`） | 主按钮、当前锚点、cite 角标、阶梯已完成段、正文链接 |
| 辅助色（铜） | `#9A5B2C`；文字深变体 `#714018`（软底 `#F3E7DA`） | 层级标签、进行中阶梯段、数据质量提示；软底上的文字一律用深变体保证 ≥4.5:1 |
| 墨色 | `#23262B` / 次级 `#5F646B` / 分隔线 `#DAD5CB` | 正文、次要文字、边框 |

## 5. 页面布局

- **导航结构（唯一）**：无导航栏、无侧栏、无面包屑。单页纵向滚动，右侧固定**锚点进度条**：竖向轨道（滚动填充）+ 5 个点位（关键发现 / 取舍对比 / 理由 / 行动项 / 证据），当前层由 IntersectionObserver 判定并高亮，轨道填充由 scroll 监听驱动。
- 栅格：内容列 `max-width:980px` 居中，单栏到底；简报内部层级用留白（`padding:44px 0`）而不是分隔容器。
- 密度低：结论卡一屏一张，卡间距 18px，行长 68ch。
- 断点：1440（完整锚点条，点位带 hover 标签）/ ≤1200（条右移贴边）/ ≤900（**降级为纯点位**，hover 标签隐藏，正文右侧让出 34px——锚点条不整体消失，位置感承诺在小屏仍然成立）/ 768 不破版，表格窄化可读。
- 顶部存在一条"原型机制条"（声明 + 视图切换），它在 DOM 上属于 Demo 检视器而非产品界面；产品落地时不存在。

## 6. 登录页面

居中 420px 单卡，品牌表达只有一行 kicker `AI MARKET INTELLIGENCE STUDIO`，无插画无大图。视觉重点是"账号/密码 + 一枚按钮"，按钮文案即承诺结果：**进入决策简报**（因为登录后落地页就是简报，这是"无导航栏"设计的入口闭环）。

必须覆盖的四种模式（Demo 内 chip 切换演示）：
- **常规**：`POST /auth/login`，HttpOnly `mis_session`，会话 8h。
- **首次部署 `needs_bootstrap`**：`GET /api/auth/me` 返回 needs_bootstrap 时，顶部出现深绿提示条"检测到首次部署，请先创建管理员账号"，表单追加"确认密码"，提交走 `POST /auth/bootstrap`，按钮文案变为"创建管理员并进入简报"。
- **401**：统一失败文案"账号或密码不正确"，不泄露账号存在性。
- **429**：`尝试过于频繁，请稍后再试 · 429 · Retry-After: 30s`，期间提交按钮禁用。

## 7. Dashboard / 工作台

本方案**没有独立工作台**：决策简报首屏就是第一屏。信息组织：

1. 简报头版：标题 + 状态 chip（中文 + 原始枚举 `SUCCESS` 供查证）+ 运行号 + 数据集名 + **数据截至** + 生成时间 + `llm_used`。
2. 头版右下角只有两个出口按钮：`发起新的分析`、`查看完整报告`。这是"无导航栏"下唯一的行动分叉。
3. 第一层"关键发现"：≤5 张结论卡，每张 = 一句话结论（可被直接引用进 PPT）+ 一句理由 + `cites` 角标（T1/T2），角标点击滚动到底部证据区并短闪高亮。

数据全部来自最近一次 SUCCESS 运行的 `GET /api/workflows/{id}/report`（结论卡 = `summary` + 各 `sections[].heading/text` 的提炼呈现）与 `GET /api/workflows/history`（取"最近一次"）。

## 8. Market Analysis（完整路径）

选数据集 → 输入需求 → 发起 → 看 Agent 状态 → 看结果，三步一块的纵向卡片：

1. **选数据集**：列表来自 `GET /api/datasets`（默认 limit 50；文件名搜索 `q` 是真实参数，保留）。每项显示列数/行数/上传时间（详情接口补充画像摘要）。
2. **提出需求**：`question` textarea，2–500 字，实时字数计数。
3. **执行预算**：`max_steps` 滑块 1–8，`output` 同步显示。
4. **发起**：`POST /api/analysis` → **202 已受理**横幅：显示返回的 workflow id、说明前端将以 1000ms 轮询 `GET /api/workflows/{id}`，并提供"查看运行进度"出口。
5. 终态后自动跳回简报首屏（结论卡按层级顺序展开）。

## 9. Agent Runs

- 进度呈现**只用 `step_index / total_steps` 阶段阶梯**：7 级对应 7 个非终态流程枚举，原样可查证（title 提示 `PENDING/PROFILING/PLANNING/EXECUTING/CHARTING/REPORTING/VALIDATING`；终态 `SUCCESS / SUCCESS_WITH_WARNINGS / FAILED` 出现在状态 chip）。已完成段决策绿、当前段铜色（120–200ms 背景过渡），**严禁任何阶段耗时/时间戳/百分比进度**；如需时间只允许整条任务真实总耗时（`created_at/finished_at` 差值）。
- 任务简报表：`task_id / description / status`，任务状态 6 枚举中文映射且保留原始值（含 `SKIPPED 已跳过` 并说明跳过原因文本来自接口）。
- 明确标注：轮询 1000ms、无推送；图表 PNG 终态后经 `/charts/{filename}` 加载。
- 空/加载/错误三态在简报语境下各自有形态：骨架行 + 阶梯（加载）、三种成因空态（还没有数据 / `q` 筛选无结果 / 读取失败）、401/429/FAILED/校验 error 四类错误卡。

## 10. Reports

两态共存：
- **简报态**（默认）：结论卡栈 + 取舍矩阵 + 节选推理段落 + 行动层 + 证据层。每张结论卡标注"来自 section「××」"，即 `sections[].heading`；`cites` 角标是卡片的组成部分。行动项逐条来自 `sections[].text`，页面明示"是报告内容，不是任务系统"，不提供新建/指派/截止日/勾选。
- **完整报告态**：`title/summary/sections[]/data_quality_notes/citations/generated_at/llm_used` + 校验 severity（error/warning/info chip）全量线性呈现，同样带角标，可跳回简报证据层。

**取舍对比矩阵的数据来源（只有两条合法路径，Demo 注释已写明）**：
(a) 单次报告内真实工具产出——`compare_groups` / `top_n` / `correlation` 的结果表直接渲染；
(b) 对**两次真实运行**分别调 `GET /api/workflows/{id}/report`，前端并排抽取报告数值（需要两个真实 workflow_id，Demo 中 #WF-2213/#WF-2219 为占位）。禁止编造模拟数字对比。

## 11. 动效

| 动效 | 时长 | 业务价值 |
| --- | --- | --- |
| 阶梯段落背景色过渡（等待→已完成） | 160ms | 轮询到状态推进时给出"任务真的在走"的确认，不闪烁 |
| 锚点当前点位高亮 + 轨道填充 | 150ms | 高管随时知道自己在"答案/理由/证据"哪一层，替代导航栏 |
| cite 角标点击后目标证据卡边框短闪 | 1200ms 衰减 | 完成"结论→证据"的视线交接，证明可追溯不是装饰 |
| 加载骨架脉冲（透明度 0.55→0.2） | 1.2s 循环 | 报告文本未返回期给等待预期；prefers-reduced-motion 全部关闭 |
| hover 锚点标签淡入 | 150ms | 键盘/指针可达性提示，仅可达性，无装饰缩放 |

## 12. 优点

- 决策友好度全场最高：30 秒内拿到可引用的结论，无需理解"数据集/工作流"概念。
- 可追溯性以最不打扰的方式常驻：角标 + 证据层，不牺牲低密度。
- 无导航栏 + 锚点条使页面本身成为阅读脚本，汇报路径即产品路径。
- 落地成本主要在报告解析与呈现层，后端零新增接口。
- 与 03/05/10 同属"低密度叙事"但 DOM 结构（卡片栈）、交互机制（锚点高亮）明确区分。

## 13. 缺点

1. **信息上限低**：结论卡 ≤5 张 + 单一矩阵，多问题混合分析（一次运行回答 4 个问题）会被压缩到失真；必须靠"完整报告"兜底，高管可能漏掉未被提炼进卡片的警告。
2. **取舍矩阵落地难度被低估**：路径 (b) 需要前端从两份异构报告的自由文本 `sections[].text` 中对齐"同一维度"，语义匹配不可靠（LLM 报告没有结构化对比 schema），可能大量情况只能退回路径 (a)，矩阵覆盖面受限。
3. **行动项无法闭环**：后端没有任务系统，行动建议只能看不能管；高管的第一反应恰恰是"谁来办、何时办"，期待落差需要产品话术管理。
4. **无导航栏的双刃剑**：dataset/history/settings 等 6 个既有视图只能靠简报头版两个出口 + 页内链接可达，功能可发现性差；小屏锚点条降级为纯点位后位置感进一步减弱。
5. **强依赖报告质量**：结论卡提炼直接吃 `summary` 与 `sections[].heading`，一旦报告标题口语化，卡片首句质量随之崩塌，前端无法补救。

## 14. 适合的企业类型

决策链条短、以高管汇报为驱动的公司：消费/零售品牌的战略与经营分析部、PE/VC 投研后市场验证、咨询公司给客户的"一页纸交付"场景。不适合需要分析师深度操作全量功能的研究型团队（选 01/06/07）。

## 15. 推荐指数

★★★★（4/5）。理由：在"让非分析背景决策者 30 秒内采信 AI 结论"这一目标上没有对手；扣一星是因为它作为**唯一界面**会牺牲平台可操作性。什么情况下选它：产品定位是"给高管的决策入口"而非"给分析师的工作台"，或作为 01/06 落地后的第二入口（简报模式）。若需要保留完整功能导航且仍偏叙事，选 03；若追求极简到一屏一个数字，选 05。

## 附：与现有代码的落地影响

**"无导航栏"如何与现有 6 个视图（`workbench/dataset/analysis/report/history/settings`）共存**：
不删除任何视图，改变的是**默认与层级**——登录成功后的落地视图从 workbench 改为新增的 `view-brief`（决策简报）；简报自身只带两个出口（发起新分析→analysis、查看完整报告→report），其余视图收进"完整报告"页脚与简报头版次要链接（`history/settings`），即"导航降级为出口"。现有 `index.html` 的 `data-view` 切换机制原样复用，`app.css` 增加 `#view-brief` 与 `.anchor-rail` 布局段，`app/web/tokens.css` 增补本方案色对（--paper/--ink/--green/--copper 族）。`app.js` 需要的渲染函数：`renderBrief()`（把已缓存的 report JSON 拆成结论卡/矩阵/证据层）、`initAnchorRail()`（IntersectionObserver + scroll，约 40 行）、矩阵对比的 `renderTradeoff()`（路径 a 直接画工具结果表；路径 b 对两个 workflow_id 各调一次现有 report 接口后前端并排抽取）。

**涉及文件**：`app/web/tokens.css`、`app/web/app.css`、`app/web/index.html`、`app/web/app.js`（新增 3 个渲染函数 + 视图注册）。

**是否需要动后端：不需要。** 简报所需的 `GET /api/workflows/{id}/report`、`GET /api/workflows/history`（取最近 SUCCESS）、`POST /api/analysis`、轮询接口均已存在；结论卡提炼复用报告生成时已有的 `summary/sections`，不新增 LLM 调用。唯一潜在后端需求是"为两次运行做结构化对比 schema"（缺点 2），本方案明确**不**为其加接口，用前端抽取 + 路径 (a) 兜底，故不破坏任何现有能力。
