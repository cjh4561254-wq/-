# 方案 02：AI 原生智能体工作台

> 坐标（取自 `00-brief-and-matrix.md` 第 3 节，不得偏离）：**无传统侧栏菜单**；左 = 分析会话/任务列表 220px，中 = 可继续的对话式指令流，右 = 运行轨道 rail 180px；密度中；数据主角 = Agent 任务卡与产出物；主题亮。
> 立场：分析是"和一组 Agent 协作"，不是"填一张表单"。
> 配套 Demo：`design-options/option-02/index.html`（单文件、零外部依赖）。

---

## 1. 设计名称

**AI 原生智能体工作台**（Agent Workbench / 以会话为组织的三栏协作面）。

界面里没有"功能页"这个东西。用户看到的单位是**一次分析会话**：我问了什么、Agent 接下来做了什么、产出了哪几张图和哪份报告、我能不能接着往下问。左栏是会话，中栏是这个会话的时间线，右栏是这一次运行走到哪一步。

---

## 2. 核心设计理念

这套方案想表达的是：**"提问—等待—拿结果"不是一个表单流程，而是一段有记录、可续问、可质证的协作过程**。所以界面不用"模块"来切，而用"会话"来切：进入产品就是回到我上一次的分析，中间那条指令流既是操作界面也是审计记录——每条 Agent 发言都对应一次真实的工具调用（`describe_dataset` / `group_aggregate` / `top_n` / `missing_values` / `compare_groups` / `correlation` / `time_series_summary`），每张任务卡背后就是后端 `TaskBrief` 的 `task_id / description / status / error` 四个字段，没有任何一行界面文字是装饰。右轨只说一件事：`step_index / total_steps`——第几步、共几步，绝不假装知道每个阶段花了多久。

同时它必须**克制"AI 炫技"**。产品确实由智能体驱动，但可信度来自"每条结论都能落到一个可复算的工具调用上"，而不是渐变、发光、星星和一颗巨大的机器人头像。因此视觉上走"编辑排版"路线：暖白纸面、细线分栏、墨色文字、状态靠语义色 + 形状 + 文字三重编码、图表一律中性灰阶。AI 的存在感由"它在替你做事并把做法摊开"来体现，而不是由特效体现。

对前端不可为的事同样诚实：接口是 1000ms 轮询，界面就只说"轮询中"，不画实时日志流；后端没有报告导出、没有数据集删除，界面就不给这两个按钮留一个像素。

---

## 3. 视觉关键词

纸感、墨线、轨道、任务卡、可追溯。

（补充说明：`纸感` = 暖白底 + 无阴影分层；`墨线` = 用 1px 细线而非卡片投影建立层级；`轨道` = 右栏那条 180px 的垂直阶段阶梯；`任务卡` = 数据主角；`可追溯` = 角标 `T1/T2` 与来源行。）

---

## 5. 页面布局

**三栏 + 顶栏，没有侧栏菜单。**

```
┌────────────────────────────── 顶栏 48px ──────────────────────────────┐
│ 市场情报与智能分析平台   当前会话上下文   视觉方案示意·数据为占位样例·未接入后端   账户 │
├────────────┬──────────────────────────────────────────┬──────────────┤
│ 左 220px   │ 中  minmax(0,1fr)                        │ 右 180px     │
│ 分析会话   │ 对话式指令流（可继续）                    │ 运行轨道 rail │
│ 列表       │  · 用户提问轮                             │  · 第 3/6 阶段│
│  · 状态点  │  · Agent 计划轮                           │  · 6 节点阶梯 │
│  · 问题摘要│  · TaskBrief 任务卡（数据主角）           │  · 轮询指示   │
│  · 数据集  │  · 产出物：图表框（PNG 位）+ 报告卡       │  · 产出物计数 │
│  · 分页    │  底部：composer（数据集芯片 / max_steps / │  （不放时间） │
│  无搜索框  │  发起分析）                               │              │
└────────────┴──────────────────────────────────────────┴──────────────┘
```

- **顶栏**：48px，全宽，1px 下边线。左：品牌文字（中文全称 + 小号英文副名）。中：当前会话上下文（数据集名 + `W-2214`）。右：**占位声明**（等宽小字，`#5A5C63` on `#F6F5F2`，实测对比度 6.1:1，不遮挡任何内容）+ 原型视图切换 + 账户。声明条不跟随滚动，但也不做遮罩层。
- **左栏 220px**：标题「分析会话」+ 新建按钮（进入"市场分析"的空会话，不是打开菜单）。条目 = `GET /api/workflows/history` 的一行（问题摘要 / 状态符号+中文 / 数据集名 / `created_at`）。**只有 `limit`(1–100，默认 20) + `offset` 分页**，因此左栏没有搜索框、没有排序头、没有状态筛选器——那三个后端都没有。底部两行分页控件（`‹ 上一页 / 下一页 ›` + "第 1–20 条，共 47 条"）。
- **中栏**：可变宽，内容最大可读宽 78ch；指令流 `<ol class="stream">`，每条轮次 `<li class="turn">`，左对齐区分角色：用户轮（墨色正文，无容器底色）/ Agent 轮（白底 + 1px 细线 + 3px 左侧赭石短线表示"这一步产出了东西"）/ 任务卡（白底 + 网格线 + 等宽 `task_id`）。底部 composer 固定：多行输入（2–500 字实时计数）、数据集芯片（点开是数据集面板，含真实的文件名搜索 `q`）、`max_steps` 1–8、`发起分析`（主按钮，`#2A3550`）。
- **右栏 180px**：垂直轨道。表头 `第 3 / 6 阶段`（就是 `step_index / total_steps`，别无其他数字）。6 个节点：读取数据 / 制定分析计划 / 计算 / 生成图表 / 撰写报告 / 校验数字，节点间 1px 基线，已完成段实心、未开始段虚线。其下两块：轮询指示（"每 1000ms 查询运行状态"）、产出物计数（图表 3 · 报告 1 · 校验问题 2）。**轨道里没有任何时间/百分比/速度。**
- **栅格**：中栏与右栏使用 `display:grid; grid-template-columns:220px minmax(0,1fr) 180px`；三栏各自 `overflow:auto`，整页不出现横向滚动。
- **断点**：1440px（三栏全开，中栏最宽）；1200px（右栏保持 180px，中栏收窄，可读宽降到 68ch）；**≤860px**（768 档）：左栏收起为顶栏「会话」按钮唤出的浮层（真实导航入口，非假按钮），右栏 180px 轨道**转成中栏顶部一条横向 6 段阶梯**（保留 `step_index/total_steps` 与阶段名），任务卡转单列；表格（画像/校验/来源）转为"标签—值"堆叠，禁整页横向滚动。
- **不做**：面包屑、折叠侧栏菜单、Tab 组、底部状态栏假指标、全局搜索、通知中心、保存视图。

## 6. 登录页面

单栏居中偏左的"信纸"式登录，宽度 420px，纸面 `#FFFFFF` + 1px `#CFCCC4` 边框 + 左上角一条 3px 墨蓝短线作为唯一装饰。

- **常规模式**（`POST /auth/login`）：标题「欢迎回来」，字段 用户名 / 密码，主按钮「登录」。失败一律显示后端统一文案「用户名或密码不正确」，不区分"用户不存在/密码错"，不显示尝试次数。触发限流时（429 + `Retry-After`）按钮进入禁用态并显示「操作过于频繁，请在 28 秒后重试」，倒计时结束后自动解禁——这条是真实响应头的翻译，不是装饰。
- **首次部署模式 `needs_bootstrap`**（`POST /auth/bootstrap`）：整块标题换成「初始化：创建第一个管理员账户」，副文案说明"当前系统还没有管理员，本表单只用于首次建号，建成后会进入常规登录"。字段变为 用户名 / 密码 / 确认密码（前端只做一致性校验，强度交给后端），按钮「创建管理员」。右上角一枚小字标签 `needs_bootstrap`（等宽、次要色），因为这是后端返回的真实标志位，界面上要让它可查证。
- **服务状态脚注**（`GET /api/health`）：一行小字三格：`服务 正常` / `大模型 已配置` 或 `大模型 未配置（分析结果将由规则模板生成）` / `上传目录 就绪`。`llm_configured=false` 时必须在这里显式说明，避免用户以为分析功能坏了；`uptime_seconds` 折算成"已运行 3 小时 12 分"这种自然中文。
- **视觉重点**：只有一个——主按钮。其余全部靠字号与间距分层。没有插画、没有机器人、没有渐变。品牌表达 = 一句价值主张「把市场数据变成可追溯的决策依据」（18px，`#1C1D21`），登录后在工作台首屏同样位置复现一次。
- **成功之后**：不弹提示，直接进工作台首屏（可继续的指令流），左栏加载会话列表。

## 7. Dashboard / 工作台

**第一屏 = 一条可以接着问的指令流**，不是指标看板，也不是任务队列列表。

- 顶栏下方第一行是会话标题（我这次分析的问题原文 + 数据集 + 状态符号），它取代了"页面标题"的角色。
- 指令流默认呈现最近一次**未完成或刚完成**的会话：
  1. 用户轮：问题原文。
  2. Agent 计划轮：一句话说明拆解思路 + 6 步计划列表（对应真实阶段名，不给时间）。
  3. 任务卡序列：`T1 describe_dataset · 数据集整体画像`（已完成）→ `T2 missing_values · 关键字段缺失率`（已完成）→ `T3 group_aggregate · 按区域与渠道聚合份额`（正在执行）→ `T4 top_n`（等待中）→ … 每张卡四行结构：`task_id`（等宽）/ 标题（真实工具名 + 中文说明）/ 工具类别标签（后端有**两个不同字段**，落地时别贴错：工具 `category` ∈ profile/aggregate/rank/quality/compare/trend，见 `app/tools/registry.py:183-411`；任务 `kind` ∈ describe/aggregate/compare/trend/missing/correlation，见 `app/schemas_workflow.py:125`。本方案卡片主标签用 `kind`，`category` 作为次要说明）/ 状态（色+形+字）。
  4. Agent 收口轮（运行结束时）：一句结论 + 产出物（图 3 张、报告 1 份），给"打开报告"的锚点。
- 底部 composer 常驻，输入框占位「接着问：例如 换成按月看华东的变化」。
- **信息组织原则**：任何"跨会话聚合"的诉求都放左栏（分页的历史会话），不在中栏堆统计卡；中栏永远只讲一件事——这一次分析走到哪了。
- 左栏底部允许一个小按钮「发起新分析」（跳"市场分析"空会话）；除此之外没有菜单。

## 8. Market Analysis（完整路径）

一条连续动作，全程不换"页面"，只在同一条指令流上追加轮次：

1. **选数据集**：点 composer 上的数据集芯片 → 浮出数据集面板：`GET /api/datasets` 列表（文件名 / 行数 / 列数 / `uploaded_at`），支持真实搜索参数 `q`（文件名子串，≤200 字）与 `sort`∈{uploaded_at, filename, rows} + `order`，分页 `limit/offset`。每行一个「选用」动作。面板右上角「上传数据集」→ `POST /api/datasets/upload`（multipart `file`，CSV/Excel），上传成功后直接插入列表首行并自动选用；**面板里没有删除/重命名/覆盖**，因为后端没有。
2. **输入需求**：composer 多行，2–500 字实时计数（不足 2 字或超 500 字时主按钮禁用并在按钮下方一行说明原因，不弹 toast）。
3. **设置步数**：`max_steps` 1–8，默认 6，用一行小字解释"步数越多，Agent 会做多几轮交叉验证"。
4. **发起**：`POST /api/analysis` → **202**。界面立即在流里追加用户轮 + 一张"已受理"回执卡（显示返回的 `workflow_id` 与"等待中 `PENDING`"），并**不谎报成功**：202 只代表进入队列。回执卡里写清"运行结果将每 1000ms 查询一次"。
5. **看 Agent 状态**：右轨从 `第 0/6` 起逐格推进；任务卡状态按 `TaskBrief.status` 变化（含 `RETRYING`「重试中」与 `SKIPPED`「已跳过」）；状态推进用 120–180ms 位移+透明度提示，轮询刷新本身**不做闪烁**，同状态重复轮询完全不重绘。
6. **看结果**：出图阶段完成后，流内出现产出物轮：图表框（真实是 `GET /api/workflows/{id}/charts/{filename}` 的 **PNG 二进制**，原型内用 1:1 等比灰阶线稿占位并在框下标注真实请求路径与图型中文名 柱状图/折线图/饼图/散点图）；报告完成后出现报告卡（标题 + 摘要首句 + `cites` 数量 + 「查看报告」）。
7. **续问**：composer 保持可用；同一会话内的追问沿用 `dataset_id`，但界面必须写明"追问会作为一次新的分析运行提交"（后端没有增量改图能力，不能暗示可以原地改）。
8. **失败/中断**：`FAILED` 时在流里追加错误轮（红 `✕` + 后端 `error` 原文 + 一句中文解释 + 「重新发起」按钮）；`RETRYABLE=SERVICE_UNAVAILABLE` 才给"重试"，其余失败只给"调整问题或步数后重新发起"，不给无意义的重试。

## 9. Agent Runs（执行过程可视化）

**只有两种阶梯，且都不按时间算。**

- **阶段轨道（右栏，常驻）**：6 个节点，`step_index / total_steps` 是唯一数字。节点态四种：未开始（虚线基线 + 空心圆 + `等待执行`）/ 进行中（实心方块 + `正在执行` + 一条 2px 扫描线）/ 已完成（勾 + 实心段）/ 失败（叉 + 该段变砖红并截断后续基线，其后节点自动显示 `未执行`）。终态必含 `SUCCESS_WITH_WARNINGS`（三角 + 带警告完成），三个终态一个都不能漏，否则这类运行会永远转圈。
- **任务卡流（中栏）**：粒度到 `task_id`，卡片可点开一行"输入/输出摘要"（来自 `description` 与真实列名），失败卡展开显示 `error` 原文。类别标签用工具类别 profile/aggregate/rank/quality/compare/trend，卡片标题用真实工具名。
- **明确禁止**：任何"PROFILING 3.2s"、阶段时间戳、甘特条、按时间推算的百分比、预计剩余时间、实时日志滚动流。界面唯一能出现的与时间有关的东西是 `created_at / finished_at` 折算的**整条任务总耗时**（且只在报告页作为元信息出现一次）。
- **运行列表页**（`Agent 运行` 视图）：仍然是指令流形态，但会话切换器换成"我的运行"分面：两条并列展示——一条 `带警告完成`（含 2 条校验 warning）、一条 `失败`（`T4 top_n` 执行失败，后续 `T5/T6` 已跳过）。左栏仍显示这些运行所属的会话。
- **轮询语义要被看见**：轨底一行小字「每 1000ms 查询运行状态 · 上次更新 2 秒前」；"上次更新"由前端本地计时，不来自接口时间戳，界面上要注明这点，避免被误读成阶段耗时。

## 10. Reports（报告呈现与可追溯）

报告仍是**同一条指令流的终点产物**，不跳去独立文档站；但报告视图内用与流一致的排版（白底纸面 + 最大 72ch）。

- 结构映射接口字段：`title` → 报告大标题；`summary` → 首段摘要（18px，唯一放大的正文层级）；`sections[]`（`heading / text / cites[table]`）→ 编号小节（01/02/03…）；`data_quality_notes` → 小节末尾一条赭石竖线引出的「数据质量说明」；`citations` → 文末「来源」表格；`generated_at` → 元信息行「生成时间 …· 数据截至 …」；`llm_used` → 一行说明正文来源（`大模型撰写` / `规则模板生成`），因为它直接改变用户对措辞可信度的预期。
- **`cites` 是本方案最用力的地方**：正文每个关键数字后紧跟角标 `[T1]`（赭石 `#8A6A3C`，等宽，小号，可聚焦、可键盘触发）；激活后滚到来源行并 150ms 高亮该行的左竖线。来源行结构：`T1 · group_aggregate · 按区域×渠道聚合市场份额 · 数据集 market_2024_q4.csv · 列 region/channel/share_pct · 共 128 行参与计算`。点来源行的工具名可以把指令流滚动回对应任务卡（同页锚点，不是跳转外部）。
- **校验结果**：小节标题右侧一枚状态符号 + 计数（`校验：0 错误 · 2 警告 · 1 提示`），展开后按 `severity` 分三档 `error / warning / info` 各一行（色+形+字），每条写明"哪一节哪个数字被质疑、后端给出的理由"。`error` 存在时报告标题下方一条砖红细线（不是弹窗）。
- 表：画像/分组结果表用真实 `<table><th scope="col">`，窄屏转"标签—值"堆叠。
- **不做**：导出 PDF/CSV/JSON、下载、分享链接、评论、收藏、发送给他人——后端一个都没有，界面一个按钮都不放。报告页唯一的出口动作是「回到这次会话继续问」。

## 11. 动效

| 动效 | 参数 | 业务价值 |
| --- | --- | --- |
| 阶段节点推进 | 140ms，`translateY(2px)→0` + 透明度 0→1，仅新变为"进行中/已完成"的节点触发 | 让"分析确实在前进"可被眼睛追踪，替代了被禁止的时间百分比 |
| 任务卡状态变化 | 160ms 底色从 `#FFFFFF` 到 `#FBFAF8` 的一次性过渡 + 符号替换（即时） | 状态是这套界面的核心事实，变化必须可察觉但不闪烁 |
| 新轮次入流 | 180ms `translateY(6px)→0` + 透明度 | 长运行中用户能立刻定位"新内容从这里开始"，避免以为界面重复 |
| 引用角标 → 来源行高亮 | 150ms 左竖线宽 2px→3px + 背景一次淡入 | 溯源必须"点得到、看得见落点"，这是产品核心差异 |
| 进行中节点的 2px 扫描线 | 1.8s 线性循环，只在节点态为"进行中"时存在 | 区分"轮询持续拿到同一状态"与"界面卡住了"；它明确表示"还在跑"，不表示进度或耗时 |
| 数据集面板/账户浮层开合 | 120ms 透明度 + 4px 位移 | 减少"内容凭空出现"的迷失感 |
| 按钮禁用态 | 无动画，仅符号与文字变化 | 校验失败的解释靠文字，不靠抖动或闪烁 |

全局：`@media (prefers-reduced-motion: reduce)` 下所有位移/循环关闭，仅保留颜色变化；轮询刷新不做任何闪烁或缩放；hover 只做可达性提示（下划线、边框加深），没有缩放。

## 12. 优点

1. **心智模型和产品价值一致**：用户来是为了"让 Agent 替我分析并给可追溯结论"，界面就正好是"我和一组 Agent 的协作记录"，不需要用户理解"模块/页面"概念。
2. **可追溯性被自然强化**：指令流里"工具调用 → 图 → 报告结论"是同屏上下关系，`cites` 只是把这条既有关联点了一下，说服力比"另开一个报告页"更强。
3. **续问成本极低**：composer 常驻且始终绑定当前会话的 `dataset_id`，同一数据集上做多轮分析这条真实高频路径最短。
4. **实现面小**：三栏 + 一个流 + 一个轨道，几乎没有需要新写的复杂容器；现有 `renderTasks / renderCharts / renderReport / renderValidation` 的产物可以直接嵌进流里。
5. **不需要任何造假**：布局天然只需要 `step_index/total_steps` 与 `TaskBrief`，不强迫界面去显示后端根本没有的阶段耗时、队列吞吐、用量成本。
6. **视觉可信度高且不投机**：暖白纸面 + 中性灰阶图表 + 三通道状态编码，不依赖任何"AI 感"装饰，两年后回看不会显得廉价。

---

## 13. 缺点

1. **"会话"这一层在现有后端是虚的**：`GET /api/workflows/history` 只有 `limit/offset`，一次分析 = 一条 workflow，没有跨多轮追问的 conversation 实体。要做左栏那种"点进来接着问"，只能前端本地按 `dataset_id` 聚合或每次追问都新建 workflow 再拼回去——聚合规则一变，会话列表的语义就漂。这是真实实现成本，且左栏不能搜索/筛选（后端没有），会话超过 20 条后找回体验会明显变差。
2. **长运行会把流拉得很长**：`max_steps` 到 8 时任务卡 + 图表 + 报告卡混排，流可超过 3 屏；关键结论被稀释，"最该看见的那一个数字"反而不显眼。缓解（折叠已完成阶段）又与"每条都要看得见"的可追溯诉求直接冲突。
3. **右栏 180px 信息量天然很低**：只有 6 个节点和两行元信息，且被 2.2-3 禁止放时间/百分比。在 1440px 屏上它是"占位但不多产"的一栏，容易被评审误读为浪费，也容易被业务方要求往里塞图表缩略图/日志（那些都不该进）。
4. **对话式界面会诱发超出后端的期待**：用户会输入"把第二张图改成红色""只看华东"这类指令，而后端只有 `question + dataset_id + max_steps`，没有条件注入、没有改图接口。界面必须显式说明"每次追问都是一次新的完整分析"，否则会被当作智能体可以任意指挥的聊天机器人。
5. **中密度 + 暖白对实现敏感**：纸感底色一旦在不同显示器上偏黄，细线与文字对比度会同时受损；且没有暗色主题做补偿，长时间盯屏的用户在暗环境会不适。
6. **弱导航对"非分析型任务"不利**：没有侧栏菜单，改密码、看登录设备会话这类低频操作只能塞进顶栏账户浮层；随着后端能力增加（比如更多真实接口），这套结构没有给"功能页"留扩展位，迟早要重排。

---

## 14. 适合的企业类型

- 分析师人数不多（1–15 人）但每张结论都要被追问依据的团队：经营分析、市场研究、咨询项目组。
- 决策链短、以"问题—报告"为工作单元的组织；用户愿意用自然语言表达需求，且能接受"一次运行几分钟"的异步感。
- 已上线本产品但不想再培训一套 BI 术语（维度/度量/面板）的企业；希望界面像协作工具、成果像交付物。
- **不适合**：需要跨用户监控平台运行状况、看队列与吞吐的运维视角（选方案 09）；需要极密表格与纯键盘操作的专业数据终端用户（选 04）；把报告当正式出版物归档、重视编号节奏的品牌/研究部门（选 03 或 10）。

## 15. 推荐指数

**★★★★☆（4 / 5）**

理由：这是唯一一套把"多智能体流水线 + 数字可追溯"这两个真实后端卖点直接变成界面结构的方案，落地成本还低；扣分在于"会话层"要额外定义、长流的可读性风险与 180px 轨道的低信息量。

什么情况下应该选它而不是它：如果客户第一诉求是"我要一屏看到整个团队跑了多少任务、哪些失败了"，选 **09**（平台运维视角，队列 + 泳道 + 事件流，组织单位是任务不是我的会话）；如果诉求是"我要一份能直接读、章节清楚、像咨询交付物的报告"，选 **03**（报告文档流为主角，交付物即界面，不做对话式操作）；如果诉求是"分析师每天在几个数据集上高频换维度跑数"，选 **06**（顶部一级导航 + 页内二级 Tab，功能页组织，左侧无会话列表，路径更短）。
