# 方案 09：企业级 AI Operations Center

> 坐标（摘自 `00-brief-and-matrix.md` 第 3 节第 09 行，不得偏离）：
> 导航结构 = 左侧运行态泳道（按状态分组）+ 底部事件流抽屉；首屏主角 = 队列四列（等待中 / 运行中 / 已完成 / 失败）；
> 密度 = 极高；数据主角 = 状态时间线 + 事件流；主题 = 暗（外壳）+ 亮（报告）；
> 立场 = 平台可信度来自"看得见它怎么跑"。
>
> Demo：`design-options/option-09/index.html`（7 个视图：登录 / 运行中心首屏 / 事件流抽屉 / 单条任务详情 / 报告 / 发起新分析 / 空·加载·错误）。

## 1. 设计名称

**企业级 AI Operations Center**（内部简称"运维台"）。

命名要点：不叫 Dashboard、不叫工作台、不叫控制台。它是一套**运行态视图**——面向把分析平台当成生产系统来对待的人：数据平台负责人、SRE、被问"昨晚那批跑得怎么样"的人。

---

## 2. 核心设计理念（这套方案在表达什么）

这套方案表达的一件事：**"这个平台可信"不是一个可以声称的属性，而是一个可以被查看的状态。**

本产品最有说服力的时刻，往往不在报告写得多漂亮，而在有人追问"这个数字从哪来、跑的时候顺不顺、失败了卡在哪一步"的时候。方案 09 把这些追问需要的东西放到首屏：任务现在排在哪个状态、有多少条停在运行中、已完成里有几条是带警告完成、失败的那条停在哪一步、以及发起新分析时接口有没有开始限流。为了让"看得见"不变成"演得像"，本方案把后端给不了的东西**在界面上明写出来**：阶段块等宽并标注"阶段级耗时需后端补时间戳后才能显示"；事件流标注"轮询采样 · 非实时"；每个统计指标旁边写清样本量与口径，绝不摆成全库指标。

第二个理念是**双主题不是开关，而是同屏分层**。运维外壳是暗的，因为它要在 8 小时轮班里长时间亮着；报告是白纸，因为它要被打印、要被核对、因为后端图表就是浅底 PNG。用户从暗处看运行态，从亮处读结论，视线穿过一条明确的边界——这条边界本身就是产品语义：**运行过程**与**交付物**不是一回事。

代价也写在理念里：这一套放弃了"人人都舒服"的普适性，选择对特定人群极度有效。

## 4. 色彩体系

三套色板职责严格分离，**互不借用**：状态色不用于画图，图表色不用于标状态，统计条带的单色阶不承载任何语义（"红色 = 慢"这种假因果是本界面最大风险）。所有值都实测过对比度（正文档 ≥ 4.5:1）。

## 5. 页面布局

### 5.1 骨架（1440px 档）

```
┌ 原型视图切换条（静态原型取景器，11px）──────────────────────────┐
├ 顶栏：品牌 + GET /api/health 字段 + 「外壳暗 / 报告亮」主题声明 ┤
├ 声明条：视觉方案示意 · 数据为占位样例 · 未接入后端 ─────────────┤
├ 左 210px          ┌ 统计口径条（样本量 + 口径 + "非全库"）─────┐ │
│ 运行态泳道        │ 统计带 5 卡（样本量/成功率/平均耗时/…）    │ │
│ （状态分组，       ├──────────────────────────────────────────┤ │
│  sticky，          │ 队列四列：等待中 | 运行中 | 已完成 | 失败  │ │
│  点击=筛选右列）    │ 每列 3 张任务卡（等宽阶梯 + 真实字段）    │ │
│  429 单列在列内     └──────────────────────────────────────────┘ │
├ 底部事件流抽屉（常驻：收起 34px / 展开 236px，内部滚动）─────────┤
```

- **左侧泳道**是导航：分组就是后端状态枚举的中文聚合（等待中 / 运行中 / 已完成 / 失败 / 接口限流）。它替代了传统"页面菜单"——在运维台里，"去哪里"等于"看哪一批任务"。
- **首屏主角是队列四列**，不是指标卡，不是图表墙。列内卡片是唯一可点对象。
- **抽屉常驻**，展开时把首屏底部 padding 提到 300px，保证最后一行卡片不被盖住。

### 5.2 栅格与密度

主内容 12px 外边距 + 8px 卡片间距；统计带 5 栏等宽；队列 4 栏等宽。基准字号 13px，元信息 10–11px，指标 19px，报告正文 13.5px / 行高 1.75（中文报告体必须比外壳松）。数字一律 `tabular-nums lining-nums` 等宽对齐。

### 5.3 断点（只有两档，都必须不破版）

- `≤1180px`：统计带转 3 栏、队列转 2×2、详情与发起页转单栏、阶梯转 4 列换行。
- `≤768px`：泳道转 2 列横排并解除 sticky；队列转单列（列序不变，仍是"等待→运行→完成→失败"）；任务表与来源表转"标签—值"堆叠（`td::before` 取 `data-label`），**整页不横向滚动**；抽屉条换行、展开高度按 340px 预留。
- `prefers-reduced-motion: reduce`：所有过渡与骨架脉冲降到 1ms。

### 5.4 与 01 / 02 / 04 的 DOM 层区别（防内部塌陷）

- **vs 01（战略指挥中心）**：01 首屏是"业务问题 × 结论 × 证据数"的态势带，表里装的是业务数据；09 首屏是队列，表里装的是任务数据（`task_id`/`step_index`/`Retry-After`）。01 的左栏是页面菜单，09 的左栏是状态分组过滤器。
- **vs 02（智能体工作台）**：02 的组织单位是"一次分析会话"，左侧是对话/任务列表，主角是可继续的指令流；09 的组织单位是"一批运行"，没有对话流，左侧是泳道，主角是队列 + 事件流。02 只关心一条任务，09 关心 21 条任务同时什么样。
- **vs 04（金融终端）**：04 也是暗色 + 极密 + 有状态时间线，但 04 的主角是**多窗格分屏的数据表格**，导航是顶部窗格标签 + 命令面板（Ctrl/Cmd+K），键盘可达优先；09 的导航是**左侧状态泳道 + 底部抽屉**，主角是**队列分组**，没有窗格标签、没有命令面板，鼠标/触屏路径完整可走。04 的表读的是行情，09 的列读的是运行态。

## 6. 登录页面

布局：左侧品牌面板（暗，`#0a1017`）+ 右侧表单（`#141d2b`，宽 380px）。品牌面板下方**直接显示 `GET /api/health` 的真实字段**：`status / version / uptime_seconds / llm_configured / upload_dir_ready`——运维台的登录页先回答"服务活着吗"，再回答"你是谁"。

四种返回态在原型内可切换查看（`data-authstate`）：

1. **常规**：用户名 + 密码（`POST /auth/login`，HttpOnly `mis_session`，8h）。失败统一文案，界面不做二次猜测。
2. **`needs_bootstrap`**（首次部署）：标题从"登录运维台"变成"创建第一个管理员"，出现第三个字段"确认管理员密码"（`POST /auth/bootstrap`），面板顶部一条说明：该模式只出现一次，创建后自动回到常规登录。
3. **401**：`账号或密码不正确。` —— 明写"后端对 401 返回统一文案，不区分账号不存在与密码错误"。
4. **429**：`尝试过于频繁，请稍后再试。` + `HTTP 429 · Retry-After: 34`，并说明这条会同时写入底部事件流（运维视角下 429 是容量信号，不只是失败提示）。

视觉重点：**没有装饰性插画、没有渐变**。品牌表达靠左下那三行真实健康字段——"这台机器在跑，而且状态可查"就是这套方案的品牌。

## 7. Dashboard / 工作台（运行中心首屏）

第一屏自上而下四件事：

1. **口径条**（先讲口径再讲数字）：`统计口径：GET /api/workflows/history 返回的前 68 条 items（该接口只有 limit/offset，无状态筛选、无排序）。因此下列指标是"最近取回样本"的描述，不是全库指标；成功率与平均耗时由前端计算，接口不返回任何聚合值。`
2. **统计带 5 卡**，每卡一个 `metric__scope` 行写死口径：
   - 样本量 `68 / 100 上限`（`limit=68, offset=0`，未翻页合并）
   - 样本内成功率 `86.8%`（分子含 SUCCESS 55 + SUCCESS_WITH_WARNINGS 4）
   - 样本内平均耗时 `9m 32s`（口径 `finished_at − created_at`，仅 59 条终态样本参与，阶段耗时无数据）
   - 带警告完成占比 `5.9%`（4/68，明细在报告层 `data_quality_notes`）
   - 轮询窗口内 429 `1`（口径：前端 1000ms 轮询观察到的响应码计数，非服务端统计）
3. **队列四列**：`等待中(PENDING)` / `运行中(PROFILING→VALIDATING)` / `已完成(SUCCESS · SUCCESS_WITH_WARNINGS)` / `失败(FAILED)`。每列头部同时给出中文、计数与**原始枚举值**；列头一行提示把边界写死（如运行中列："阶梯宽度相等：后端无阶段时间戳，不假装时长"）。
4. **底栏声明**：合法操作只有查看与再发起一次新分析；heartbeat_at 未暴露故不显示存活信号。

任务卡字段（全部来自真实接口）：`workflow_id`（等宽）、问题原文、数据集（`ds_xx · 文件名`）、`max_steps`、`step_index / total_steps` 阶梯、状态徽章（中文 + 原枚举）、终态样本的真实总耗时、失败卡前 3 行 `error`。
**卡片上没有取消 / 重试 / 暂停 / 重跑 / 删除 / 导出按钮**——后端没有这些接口。

左栏泳道计数与右栏列计数一致；点击泳道只过滤右列，不跳转，避免"看着看着丢了上下文"。429 在等待中列里是一块独立紫标说明区，明确标注它是接口返回码、不属于工作流状态枚举。

## 8. Market Analysis（完整路径）

运维台里的"发起一次分析"不是主入口，但路径必须完整可走（视图 `launch`）：

1. 选数据集：`GET /api/datasets`（`q` 文件名子串筛选真实存在，可以放搜索框；`limit/sort/order` 用于候选排序），行内显示画像摘要（列数 / 行数 / 缺失率 / 告警条数）。
2. 写需求：`question`，2–500 字，实时显示"已输入 31 字 / 上限 500"。
3. 定深度：`max_steps` 1–8 的等宽分段按钮（运维用户明确知道步数换的是时长与深度）。
4. 发起：`POST /api/analysis` → **202** + `workflow_id`，任务落进首屏"等待中"列（此时只有 `created_at`）。
5. 若返回 429：按钮区显示 `Retry-After` 秒数、前端暂停新发起、事件流写一条"发起被节流（未创建任务）"，运行中任务不受影响。
6. 看状态：1000ms 轮询 `GET /api/workflows/{id}`，阶梯按 `step_index/total_steps` 推进。
7. 看结果：终态后进入报告视图；`FAILED` 则停在详情的错误行 + 任务表定位失败 task。

页面上用 7 条编号步骤把这条路写在右侧面板里，其中第 7 条直接列"不可做的事"，让读者不用猜。

## 9. Agent Runs（执行过程如何视觉化）

**状态时间线（本方案的数据主角之一），两条不同的轴：**

1. **阶段轴 = 等宽七块 + 终态块**：`① 画像中 PROFILING / ② 规划中 PLANNING / ③ 执行中 EXECUTING / ④ 图表中 CHARTING / ⑤ 报告中 REPORTING / ⑥ 校验中 VALIDATING / 终态 SUCCESS · SUCCESS_WITH_WARNINGS · FAILED`。块宽**一律相等**，视觉上就是"我不假装这是时长"；每块三行：中文、原枚举值、状态词（已完成 / 当前 / 未开始 / 待到达）。
2. **真实时长轴 = 整条任务**：`created_at → finished_at`（例如 12m 08s），轴上只有两个真实锚点。等待段与执行段的**拆分**需要 `started_at` 进入轮询响应，界面用图例明写这一点。

**四句必显的降级说明**（在详情视图的 `caveat` 块里，不是藏在文档里）：

- 阶段级耗时**需后端补时间戳后才能显示**；当前阶段块等宽，宽度不含时间语义；任何"画像 3.2s"不予呈现。
- 等待段 / 执行段拆分需 `started_at` 进入轮询响应（`WorkflowState` 有该字段，接口未暴露）。
- `heartbeat_at` 未暴露，界面不显示存活信号，也不做"卡死"判定。
- 状态推进来自 1000ms 轮询差异，**非实时**，中间态可能未被采到。

**任务简报表**（`GET /api/workflows/{id}`）：`task_id`（T1…T6，等宽）/ `description` / `status` / `error` 四列，6 个任务状态各有实例（含 `SKIPPED`，虚线形 + "已跳过"文字）。窄屏转标签—值堆叠。

**校验结果**：`severity` 三档 `error / warning / info` 用等宽方角标签 + 检查项 + 说明，与报告层的 `data_quality_notes` 一致。

**队列级视图**：同一条时间线的压缩版（12×5px 阶梯格）出现在每张卡片上，因此"卡在哪一步"在首屏就能读出来。

## 10. Reports（报告呈现）

- 报告视图是**暗画布里的一块白纸**（`#0d1420` 外框 + `#ffffff` 纸面，纸面最宽 900px），顶部一条外壳级标签：`报告主题 亮色（固定，不随外壳切换）` + `GET /api/workflows/{id}/report` + 图表来源说明。这就是双主题的同屏分层实现。
- 结构：编号 kicker（含 workflow 编号）→ `title` → 元信息行（**数据截至**、`generated_at`、数据集、`llm_used`）→ `summary`（左竖线强调块）→ 编号小节 → 图表 → `data_quality_notes` → 校验计数 → 来源表。
- **可追溯是硬要求**：正文每个数字后紧跟 `T1/T2/T3…` 角标（`.cite`，点击高亮下方 `citations` 表对应行），来源表四列：角标 / 工具调用（如 `query_quantile(region, aov, 2026Q3)`）/ 产出物 / **数据截至**。
- 图表区在原型里用内联 SVG 画占位条形与折线，并写明"真实运行时这里是后端 matplotlib 生成的浅底 PNG"，配色用 `#3b6ea5 / #c0504d`（与后端一致）。
- 没有导出 / 下载 / 分享入口（后端没有）；阅读路径终点是"回队列"，形成闭环。

## 11. 动效（逐条：动效 → 业务价值）

| 动效 | 参数 | 业务价值 |
| --- | --- | --- |
| 任务卡状态推进（列间迁移） | `translateY(-3px)` + `opacity .55`，200ms | 在 21 条并发的队列里，唯一需要被眼睛抓住的是"刚才有一条换了状态"；纯静态会让人觉得队列没在动，反而去点刷新。 |
| 卡片 hover 边框变强 | `#27344a → #3a4b66`，120ms | 告诉用户这张卡整体可点（进入详情），而不是只有小按钮可点；不做缩放、不做位移。 |
| 抽屉展开 / 收起 | `max-height 0 ↔ 236px`，200ms + 箭头旋转 | 事件流是"需要时才占屏"的次要层：展开不遮挡最后一行卡片（padding 同步 74 → 300px），收起仍保留计数条。 |
| 泳道选中态 | `inset 2px` 品牌竖条 + 面板次级底，120ms | 让"我在看哪一批任务"始终可见，避免筛完找不到出口。 |
| 报告角标点击高亮 | 角标反色 + 来源行浅底，120ms | 把"这个数字来自哪次工具调用"变成一次视觉确认，可追溯必须可被操作。 |
| 加载骨架脉冲 | 1400ms 透明度 `.5 ↔ .9` | 首轮轮询未回时，页面必须表明"在等数据"而不是"没数据"——运维台的空与慢是两种完全不同的处置。 |
| 提交态 spinner | 700ms 线性旋转 | 202 已受理但列表尚未刷新之间的占位。 |

明确**不做**的动效：轮询刷新不闪烁、不整屏淡入淡出（否则运维会把刷新当成状态变化）；状态色不脉冲（`SUCCESS_WITH_WARNINGS` 靠形与字，不靠呼吸灯）；不做 hover 缩放与阴影堆叠。

## 12. 优点

1. **对"平台可不可信"这一问题的回答最直接**：追问运行状态的人，在这套界面里 3 秒内得到答案。
2. **诚实度被写进界面本身**：阶段等宽 + 三句降级说明 + 每条统计的样本口径，使这套 UI 无法被用来骗人——包括骗自己人。
3. **运维语义覆盖真实**：状态枚举 10 值中文映射且原值可查、任务态含 `SKIPPED`、校验三档 severity、**429 被当成一等状态**显示（含 `Retry-After`）。
4. **并发友好**：一屏读完 21 条任务的位置，长时间轮班可用的暗外壳。
5. **双主题各得其所**：暗壳解决"看运行"的长时间舒适度，亮纸解决"读结论"的可核对性与可打印性，绕开了 `tokens.css` 记录的"深色模式让浅底 PNG 变白斑"这个真实问题。
6. **不引入任何假入口**：合法操作只有查看与再发起，界面上没有需要后端才生效的按钮。
7. **落地路径清楚**：全部信息来自 4 个已存在接口（workflows/{id}、history、health、datasets），不改后端也能跑起来。

## 13. 缺点（真缺点）

1. **双主题落地成本是十套里最高的一档**。现有 `app/web/tokens.css` 第 32–36 行明确写了"故意不在这里启用深色模式"，且没有 `[data-theme]` 覆盖块。要落地必须新增：品牌层 `:root[data-theme="dark"]` 覆盖块（只重定义 `--ds-*`，hex 仍只能留在兼容层，否则口径漂移）、图表容器强制白底的例外规则、以及**两套对比度断言**（同一令牌名在亮/暗两种底上分别跑 WCAG 计算，`.tmp/design/contrast_check.py` 需扩展成双主题参数化）。这不是换个配色，是给设计令牌层加一整个维度。
2. **阶段等宽 = 放弃了 Grafana State timeline 最有说服力的那一维**（色块宽度即真实时长）。运维真正想知道的"卡在 VALIDATING 多久了"，在补时间戳之前显示不了，于是这套界面的核心承诺（看得见它怎么跑）被削掉了一大块，只剩"看得见它跑到哪一步"。
3. **统计口径极易被误读**。接口没有聚合能力，成功率/平均耗时只能由 `history` 前 N 条算出，且该接口无筛选无排序。哪怕每条指标都带口径行，截图传到群里之后口径行会被裁掉——这是一套会持续制造"被断章取义"风险的界面。
4. **没有实时推送，事件流的叙事能力先天受限**。1000ms 采样会合并中间态（"EXECUTING → VALIDATING，中间两阶段未采到"），对想看"过程"的人来说，它更像差异日志而不是现场直播；这个降级无法靠前端消除。
5. **极高密度对新用户与触屏不友好**。768px 以下必须把四列拉成单列，队列的"横向对比"这一核心价值随之减半；新同事第一屏会读到大量 10–11px 元信息，需要培训才能上手。
6. **面向平台/运维，对分析师日常产出帮助有限**。它不解决"怎么写下一步分析"，因此不适合作为产品的唯一界面。
7. **信息风险：坏消息被制度化放大**。FAILED/429/带警告完成在暗底高饱和色下非常醒目，若团队把运维台投屏在工位墙上，容易把偶发失败读成系统不稳定——需要配套的使用约定（例如 429 的解释口径）才能上线。

## 14. 适合的企业类型

- 把这套平台当**内部生产系统**运营的中大型企业（有数据平台团队 / SRE / 值班轮次）。
- 金融、制造、能源、电信等**运维语言天然存在**的行业：用户对"队列、状态、限流、心跳"零学习成本。
- 需要向内部客户（业务方）证明平台可靠性的团队：运维台是"给我看它怎么跑"的答复工具。
- 有多数据集、多并发分析、日任务量数十条以上规模的组织（任务量个位数时四列会长期只有一两列有东西）。

不适合：单人分析师或小型咨询团队（选 02/06 更顺手）、以交付报告为主要对外形象的场合（选 03/08/10）、需要给高层看业务态势的场合（选 01）。

## 15. 推荐指数

**★★★☆☆（3.5 / 5）**

理由：概念独一无二、与后端能力对得最紧、对"可信"这一卖点的表达最强；但它同时是**落地成本最高**（双主题令牌层 + 双份对比度断言）而**核心承诺受限最多**（阶段耗时、实时性两处必须由后端补，否则界面只能自证降级）的一套。

什么时候应该选它而不是它：如果这套产品的使用主体是分析师本人而不是运营它的人，选 **02（智能体工作台）**；如果首要交付物是报告、运行过程少被追问，选 **03 或 08**；如果既要业务态势又要运行态，正确做法是**以 01 为主界面，把 09 降级成一个次级页**——两者共享同一套"状态中文映射 + 原枚举可查 + 统计带口径"的组件语言，成本可复用。

## 附：与现有代码的落地影响

结论：**不改后端即可落地一版**（首屏所有信息来自 `GET /api/workflows/history`、`GET /api/workflows/{id}`、`GET /api/health`、`GET /api/datasets`、`POST /api/analysis`）。需要后端配合的只有两件**可选**增强，见 8。

### 1. `app/web/tokens.css`（改动最大的一处）

- 文件头第 32–36 行的"深色模式：故意不在这里启用"决策需要被**改写**而不是绕过：新增独立段落 `:root[data-theme="dark"]{ … }`（必须是第二个 :root 块，见下方测试注意事项）。
- 覆盖块**只重定义品牌层 `--ds-*`**（画布/表面/文字/线条/状态四件套/焦点环/阴影），值仍指向兼容层或新增的暗色兼容层变量；铁律不变：hex 只出现在兼容层，两处写死必然漂移。
- 需要为暗壳新增的兼容层段落：外壳三级表面（`#0d1420 / #141d2b / #1a2534`）、凹陷 `#0a1017`、两档边框（`#27344a / #3a4b66`）、三档文字（`#e9eef7 / #c3cfe0 / #9aa8be`）、7 组状态色（含 429 与 SKIPPED 的"色块 + 文字"两档）、统计带单色阶（5 档）。
- 需要显式声明**不跟随主题**的令牌：`--ds-chart-surface`（保持 `var(--n-0)` 白）、报告层全部纸/墨令牌、`--ds-chart-1..6`。这是"双主题 = 同屏分层"在令牌层的表达方式。
- 新增令牌名（避免与 04 之类暗色方案互相偷值）：`--ds-ops-canvas / --ds-ops-surface / --ds-ops-surface-2 / --ds-ops-sunken / --ds-ops-line(-strong) / --ds-ops-ink / --ds-ops-ink-2 / --ds-ops-ink-muted / --ds-ops-bar-1..5 / --ds-ops-st-*`。

### 2. `app/web/app.css`

- 新增组件段：`.lanes / .lane`（左泳道，sticky）、`.queue / .col`（四列）、`.card / .ladder`（阶梯，等宽 12×5px）、`.band / .metric / .metric__scope`、`.bandnote`（口径条）、`.drawer / .events`（底部固定抽屉，`max-height` 过渡，内部滚动）、`.timeline / .tstate / .axis`（状态时间线）、`.caveat`（降级说明块）。
- 现有 `.sidebar`（224px 页面菜单）在本方案里被 `.lanes` 取代——**不是隐藏，是语义替换**：导航单位从"页面"变成"状态分组"。
- 报告组件（纸面容器、`.cite` 角标、来源表）保留现有实现与浅底色，仅把外层页面背景切到暗色画布。
- 断点沿用文件内已声明的字面量口径（480 / 760 / 1080，媒体查询里必须写字面量，不能用 `var()`）；本方案额外需要 1180 一档，需按现有注释纪律补一句"为什么"。
- 圆角不超过 6px（`--ds-radius-surface`），不引入 `backdrop-filter` / 渐变 / `text-shadow`。

### 3. `app/web/index.html`

- 根元素加 `data-theme="dark"`；报告区块单独包一层 `[data-sheet="light"]`，保证打印与截图时报告始终是白纸。
- `<body>` 结构重排为四段：顶栏（含 `GET /api/health` 字段）→ 左泳道 `<aside>` → 主区（口径条 + 统计带 + 队列四列）→ 底部 `<div class="drawer">`。
- 声明条、空态三成因、骨架加载、401/429 错误态各一个模板容器（当前只有一个通用 `.error-box`）。

### 4. `app/web/app.js`（需要新增的渲染函数与一个采样器）

- `renderSwimlanes(groups)` / `renderQueue(byStatusGroup)`：把状态枚举 10 值映射成 4 组，中文 + 原枚举双写（映射表必须是常量，供测试断言不漏项）。
- `renderStats(historyItems)`：**前端计算**成功率 / 平均耗时（`finished_at − created_at`）/ 带警告占比 / 429 计数，并强制把 `样本量 N` 与口径字符串一起渲染（不允许出现没有 `metric__scope` 的指标）。
- `pollDiff(id, prev)`：现有轮询只渲染最新状态；本方案需要缓存上一轮状态，产出"变化事件"数组（旧态 → 新态 + `step_index` 变化 + 被跳过的阶段合并标记 + 429 记录），写入 `renderEventStream()`。间隔仍 **1000ms**，不改数值。
- `renderRunTimeline(state)`：只渲染等宽阶梯 + 真实总耗时；**禁止**渲染任何阶段时长；**禁止**读取/展示 `heartbeat_at`。
- 报告渲染（`cites` → 来源行联动）与 `task_id/description/status/error` 表格可复用现有实现，仅新增点击高亮。
- 不得新增：取消 / 重试 / 暂停 / 重跑 / 删除 / 导出 / 通知 / 全局搜索 / 成本 / 模型选择器相关代码路径。

### 5. 测试与校验需要补的断言

- `tests/test_frontend.py` 里的 `_css_tokens()` 用的是 `:root\s*\{(.*?)\n\}`（**只取第一个 :root 块**）。暗色覆盖块必须写在第二个块里，且该函数需要升级成"返回第一个兼容层块"或"合并所有块后断言"，否则会出现用了未定义令牌的假绿灯/假红灯。
- 新增对比度断言：对同一令牌名在 `data-theme=dark` 与默认亮两种底色上分别跑 WCAG 计算（正文 ≥4.5:1、大字/非文本 UI ≥3:1），重生成 `.tmp/design/contrast_report.txt`。本文件 4.2/4.3/4.6 的实测值（最低 4.70:1）可作为初版基线。
- 新增枚举覆盖断言：10 个工作流状态 + 6 个任务状态在映射表里必须全部有中文值，且原值在同一 DOM 节点内可查。

### 6. 后端（理想答案：**不动**）

两个**可选**增强，均只加字段、不改语义、不破坏现有消费者：

1. `GET /api/workflows/{id}` 的响应里加 `started_at`（`WorkflowState` 已有该字段，未序列化）→ 解锁"等待段 / 执行段"拆分。
2. 阶段级时间戳（如 `stage_timestamps: {PROFILING: …, PLANNING: …, …}`）→ 才能把等宽阶梯升级成真正的 Grafana 式 State timeline（色块宽度 = 真实时长）。在此之前，界面必须保持等宽并显示"阶段级耗时需后端补时间戳后才能显示"。
3. （同样可选）若要在运维台做"卡死判定"，需要暴露 `heartbeat_at`；否则本方案不显示存活信号。

### 7. 与 00 文件硬约束的对应自查

- 无导出 / 删除 / 取消 / 重跑 / 通知 / 全局搜索 / 协作 / 成本 / 模型选择器入口（2.2-1、2、5、6、7）。
