## 01 证据来源与效力说明

### 1.1 事实基线（`_FACTS_PACK.md`）

三套原型共用同一份事实包 `D:\个人项目01\ai-data-analyst-agent\.tmp\design3\_FACTS_PACK.md`（10 节）。它由探针脚本 `D:\个人项目01\ai-data-analyst-agent\.tmp\design3\_probe_facts2.py` 真实执行得到，输出在 `D:\个人项目01\ai-data-analyst-agent\.tmp\design3\_probe_facts_out.json`。共用它的目的：**三套原型的差异只能来自设计决定，不能来自数据差异**，否则横向比较无意义。

事实包里的关键事实（原型中出现的每个数字都取自这里）：

- 数据集 `sales.csv`：2,168 行 × 9 列，137.7 KB，画像内存 228.7 KB，8 行完全重复，5 列存在缺失值（日期 24 / 销量 18 / 销售额 18 / 利润 18 / 客户评分 27）。
- 六阶段流水线（前端文案，硬编码在 `app/web/app.js`）：读取数据 → 制定计划 → 执行计算 → 生成图表 → 撰写报告 → 校验数字。
- 真实工具共 7 个：`group_aggregate`、`compare_groups`、`correlation`、`describe_dataset`、`missing_values`、`time_series_summary`、`top_n`。
- 图表由服务端 matplotlib 生成，文件 960 × 576 PNG。
- 分组聚合结果（原型里的柱状图与排行表用的就是它）：华南 24,871,657.00 / 东北 15,890,839.00 / 华东 11,567,345.00 / 华北 8,948,124.00 / 西南 8,467,097.00 / 西北 7,989,816.00，合计 77,734,878.00；均值口径华南 70,061.01、各组平均水平 36,202.73。
- 归档库 `workflow_history`：476 条（SUCCESS 475 / SUCCESS_WITH_WARNINGS 1），其中 364 条是同一个问题「各地区销售额对比」。
- 认证规则：用户名 3–32 位字母或数字开头；密码至少 8 位且必须同时含字母与数字；登录失败统一返回「用户名或密码不正确」；429 限流；账号库为空时走「创建第一个管理员」；会话为 HttpOnly Cookie。

### 1.2 截图证据的效力边界（重要）

六张 PNG 是**真机渲染**（Playwright + Chromium，1440×900 视口，元素截图）。但必须说清三件事，避免把原型当成产品：

1. **柱状图是我按真实数值 1:1 重绘的内联 SVG，不是服务端 matplotlib 输出。** 原型要单文件、无外链，塞不进服务端 PNG。数值、坐标轴口径、`销售额_sum` 纵轴标签、`1e7` 缩放标记都照 `ui_shots` 里的真实图复刻；但**上线时这里必须换成 `GET` 到的真图**。这一点我在 direction-A.html 的图注里写明了。
2. **六阶段的耗时条与秒数（0.42s / 1.10s / …）是构图示意，没有任何实测支撑。** 我没有真实的阶段耗时数据，所以三套原型都不得把它画成"实测"。方向 A 最初的标题写成「六阶段实测耗时」，我在目视复核时发现并改正为「分析流水线 · 六阶段 + 耗时数字为构图示意（未实测）」；方向 C 干脆**不画条**，只写一行「阶段耗时未在此显示 —— 没有实测数据就不画进度条」；方向 B 在每个耗时后都带括号标注「（构图示意 0.4s）」。
3. **配色对比度是脚本算的精确值，不是我目测的。** 计算脚本 `_contrast.py` / `_contrast_final.py`，输出在 `_contrast_final.txt`。第 05–07 节里每个色值后面的比值都出自它。我对结论诚实：**有三处原始色值实测不达标，是算出来之后才改的**（见 05.2、06.2、07.2 的"实测修正记录"）。

## 02 现有产品用户全流程审查

按任务书要求逐环节走一遍。每环节给出：**入口在哪 / 现在发生了什么 / 卡点在哪**。

| # | 环节 | 现状（实测） | 卡点 |
| --- | --- | --- | --- |
| 1 | 首次访问与登录 | **当前产品没有登录页**，打开就是工作台。后端其实已有完整认证（`app/api/routes_auth.py`、`app/schemas_auth.py`：bootstrap、会话、改密、429 限流） | 界面与后端能力脱节。用户首次访问时看不到"这台机器上还没有管理员"这个真实状态 |
| 2 | 上传数据集 | 工作台上传卡片 → 选择/拖入 → 点「上传」→ `POST /api/datasets/profile` → 右侧「数据概览」出 6 个读数 | 上传后只得到 `dataset_id`（如 `90d64c90877949ba98bf6497ba1094a6`）；**刷新页面就找不回来** |
| 3 | 选数据集建分析任务 | 必须先"进入市场分析"再提问；数据集靠服务端进程内存里的 `dataset_id` 关联 | 界面上没有任何"当前选中的数据集"控件；用户无法确认"我这次分析的是哪份数据" |
| 4 | 多智能体执行过程 | 六阶段文案 + 每阶段产出（`02-uploaded.png` 之后的执行页） | 执行过程是"最终态快照"，没有可回看的阶段历史；未把"没命中的工具"显式列出 |
| 5 | 看结果与图表 | 图表走服务端 matplotlib（960 × 576 PNG），前端的 `inline SVG` 只是占位；图注写"完整分组名见报告正文" | 图表与报告正文分离在两个滚动段落；图的坐标轴缩放（`1e7`）与指标名（`销售额_sum`）直接裸露给用户 |
| 6 | 读报告 | 报告正文含"依据：T1/T2"引用与"共核对 20 个数字"的校验徽章 | **同一张六行表在"汇总口径 / 排名 / 量级分布"三段里重复渲染三遍**（`03-workflow-done.png`）；「报告编号 9805ee61」是原始 hex |
| 7 | 看历史 | `GET /api/workflows/history` 返回 `共 429 条归档记录，本页显示 20 条（limit=20，offset=0）` | 没有分页、没有筛选、没有按问题分组；`workflow_id` 全文展示；`WORKFLOW_TIMEOUT` 以纯文本混在元信息行里 |
| 8 | 退出登录 | 前端没有退出入口（因为前端没有登录） | 与后端 `delete_user_sessions` 能力同样脱节 |

**一句话结论：这不是"界面不好看"的问题，而是"界面没有把系统真实拥有的状态表达出来"。** 后端已经有 476 条归档、认证会话、7 个工具、6 阶段执行；界面上用户能看到的只有"上传、提问、报告"三件半事情。

## 03 当前 UX 问题清单

每条都绑定到具体界面元素或代码位置。**A/B/C 三套原型分别在第 05/06/07 节回应这些问题**，对照关系写在每条末尾的方括号里。

### P1 工作台首屏是"结构空洞"，不是"信息密度高"

`01-workbench.png`：上传卡片与数据概览卡片并排在 1440 宽的 2 栏网格里。未上传时右栏几乎全空（只有一行引导文字），左栏被虚线拖拽区撑高 —— 两栏高度差约 40%，画面右半部分是白的。上传后（`02-uploaded.png`）右栏突然变成 6 块读数卡，左栏反而变矮，**布局随状态剧烈跳动**。
[A：左栏固定数据体检列，读数常驻 → 消除跳动；C：KPI 卡常驻首屏顶部]

### P2 "最近分析任务"是 5 行几乎一样的记录，且把内部标识当正文

`01-workbench.png` 底部：每行结构是 `问题 / 状态成功 / 有报告 / 大模型撰写 / 创建 2026-10-15T10:20:37.755867Z / 489a25077cc64fc7850097bf1a8f4fa09`。五个问题名只有两三种变体（「按地区看销售额」「分析不同地区的销售额」「各地区的销售额汇总」），时间戳精确到微秒（`10:20:37.755867Z`），32 位十六进制 `workflow_id` 直接铺在卡片上占掉近半行宽。用户想找"上周那次对比"时，这一屏提供不了任何区分线索。
[B：改成按问题聚合的排行表（364/90/10/7/2）；C：时间收敛到 `10-16 …` + 状态徽章]

### P3 "数据集"在刷新后消失，界面上无任何解释

`.tmp/ui_probe` 记录：`GET /api/datasets` 不存在（数据集只存在服务进程内存里）。工作台底部那段解释文字写着「这块读的是服务端 SQLite 归档库（重启后仍在）。**数据集没有列表接口** —— 数据只存在服务进程内存里，所以这里不会出现『最近数据集』，刷新页面也拿不回旧的 dataset_id。」—— 这段解释**本身是对的、诚实的**，但它是把技术限制写给终端用户看。用户在界面上看到的是一段"为什么这个功能没有"的说明，而不是一个可用功能。
[A/C 都画了"当前数据集"芯片（`sales.csv · 2,168 行 × 9 列 · dataset_id 90d64c90…9a6`）——**注意：这依赖后端新增数据集列表接口，属于需要 Lead 决策的落地条件，见 11.4**]

### P4 报告页把同一张表渲染了三遍

`03-workflow-done.png` 里 `地区 / 销售额_sum` 六行表出现在「汇总口径与结果规模」「各地区销售额汇总排名」「量级分布特征」三处，内容完全相同，每处都标「依据：T1」。三段正文的差异只在文字表述（总量、排序、量级），表格是重复的。这既是**机械重复**，也是**信息冗余**：用户滚动 2,700px 看到的是同一个数字组三次。加上页面顶部还有一张 960×576 的大图，整页高度 2,717px，**报告与图表没分流**。
[B：把两条证据（sum 与 mean）合并进一张宽表，重复度归零；A：图表卡与报告折行数并列在同一屏；C：图表与报告分卡但同屏可见]

### P5 侧栏与信息架构分不清"流程"与"功能"

`01-workbench.png` 左侧分两组：分析工作区（工作台、数据集、市场分析、分析报告）、记录（历史任务）、系统（设置，带「只读」标签）。其中「市场分析」和「分析报告」是**同一件事的两个步骤**，却被提升为两个并列顶级入口；而「历史任务」明明是同一条链上的产物，却被分到另一组。设置页挂「只读」标签，说明用户能看出自己改不了东西，但看不出原因。
[C：76px 窄轨 + 只保留 6 个去向，把"步骤"和"去处"分开；A：244px 侧栏保留两级语义（分析工作区 / 记录 / 系统）但把设置从"只读徽章"改为"实际能做什么"]

### P6 数字的来源标注不一致

同一个 `2,168`，在「数据概览」标 `row_count`，在报告质量说明里叫"原始行数"，在正文里又被隐含成"去重后 2,160"。三个地方口径都对，但**界面上没有任何一处提示"这两个数不是一个数"**。
[A：左栏底部固定「口径提示」块；B：第 04 节专门写"先说清楚这份数据的三个毛病"；C：数据体检卡底部口径提醒]

### P7 失败与异常状态没有专门形态

`06-history.png` 里那条失败记录：`状态 失败 / 无报告 / 规则模板 / 创建 … / 错误码 WORKFLOW_TIMEOUT / 0123456789abcdef0123456789abcdef` —— 错误码以普通文字混在元信息行里，和成功行视觉权重相同，用户扫一屏看不出哪条失败了、下一步该做什么。
[C：状态徽章（SUCCESS / WARN）右对齐成列 + 失败色；A：状态列独立成 78px 宽列]

### P8 历史页把后端能力丢了

代码实测：`app/api/routes_workflows.py:238` 支持 `limit: int = Query(20, ge=1, le=100)` 与 `offset`；`app/web/app.js:1555` 写死 `fetchHistory(20, 0)`，`app/web/app.js:1513` 写死 `fetchHistory(5, 0)`；`app/web/app.js:1576-1579` 把「共 N 条归档记录，本页显示 M 条（limit=20，offset=0）」当**纯文本**渲染。`grep '(pager|下一页|上一页|page)' app/web/*.js` 只命中 `page-title`/`page-sub`/`aria-current="page"` —— **页面上没有任何分页控件**。476 条记录，用户只能看到最新 20 条，且看不到"还有 456 条"这个事实（那句文字只是陈述参数）。
[B：按问题分组的排行表（一屏看完 476 条的结构）；C：分页 + 筛选项；A：状态分布条 + 左侧筛选]

### P9 归档详情不深链接

`app/web/app.js:1595 openHistoryDetail(workflow_id)` 把归档详情渲染成 `table.kv` 键值表就地展开，**不跳转到报告或图表**；`app/web/app.js:382 viewFromHash()` 只认 `#/workbench|history|status` 三种路由，没有结果深链接。这意味着用户拿到一条历史后，无法把"这次分析的图和报告"发给别人，也无法在新标签页打开。
[B/C：都假设历史行可跳到报告；**深链接需要前端补路由，属于需要 Lead 决策的落地条件，见 11.4**]

### P10 未命中的能力从不展示

系统真实有 7 个工具，`03-workflow-done.png` 的报告只提到用到的（`group_aggregate`、`compare_groups`）。用户无从知道"问销售额和利润的关系"这件事系统其实做不了（`correlation` 存在但没有被命中过），于是会反复尝试无解的问题。
[B 第 02 节 / A 的"本次调用的工具"表 / C 的工具清单卡：三套都把"未命中也要显示，否则用户不知道系统还能做什么"写进界面]

## 04 三套原型的共同约束

### 4.1 硬约束（任务书 + 项目规约）

| 约束 | 执行情况（可验证） |
| --- | --- |
| 无框架、无构建、无 CDN | 三个 HTML 单文件内联 CSS。`grep -E "https?://\|@import\|<link\|<script"` 在 `.tmp/design3/*.html` 上**零命中**（实测） |
| 1440 × 900 目标视口 | 截图脚本按该视口渲染；每套至少一个构图正好落在 900px 高（A 登录、C 登录），其余构图用"真实高度"元素截图，不做截断 |
| 数字一律等宽 + `tabular-nums` | 三套都用 `Consolas/Cascadia Mono` 数字族；`--mono` 令牌统一 |

### 4.3 为什么不能做成"同一套换配色"

三套之间共享的不是配色而是**事实**。如果把 A 的骨架配上 C 的颜色，就得到"深色三栏控制台"，它既没有 A 的密度纪律（244px 侧栏 + 3 栏的结构会被大圆角吃掉），也没有 C 的时间线主导。横向比较表（第 08 节）里的每个维度差异都对应一种**信息架构决定**，不是皮肤。

## 05 方向 A：数据控制台（Data Console）

**文件**：`D:\个人项目01\ai-data-analyst-agent\.tmp\design3\direction-A.html`
**截图**：`shots\A-login.png`（1440×900，118,284 B）、`shots\A-dashboard.png`（1440×954，189,510 B）

### 5.1 设计理念

让"这台机器正在算什么"变成一块可读的仪表。控制台的伦理是**不隐藏读数**：有多少行、几列缺失、哪些工具没命中、口径差在哪里，全部常驻在视野里，不用点开。它牺牲的是"第一眼的漂亮"，换的是"连续使用 20 分钟后仍然知道自己在哪"。

### 5.2 品牌视觉方向

- 底 `#0b131c`（近黑的钢青），面板 `#101b26 / #0d1620`，**1px 分隔线 `#1e2c3a` 承担全部结构**，不用阴影、不用渐变。
- 强调色青 `#3fc9e0` 只做"界面动作"（当前导航、主按钮、阶段条）；数据色用低饱和钢蓝 `#4a7f93` 单独一档 —— 这个分离是有意的设计决定：**如果图表和按钮同色，用户会把"可点的"和"要读的"混在一起**。
- 圆角 2–3px，几乎没有"卡片"感，靠线和留白分组。

**实测修正记录（诚实交代）**：

| 原始值 | 用途 | 实测对比度 | 处理 |

### 5.3 色彩与字体

配色令牌（`direction-A.html:12-26`）：`--bg/--panel/--panel-2/--line/--line-strong/--txt/--txt-dim/--txt-faint/--cyan/--bar/--amber/--green/--red`。字体栈：`Segoe UI → Microsoft YaHei → DengXian`（界面）、`Cascadia Mono → Consolas`（全部数字与代码）。字号刻意小：正文 11.5–13px、标题 12.5–13.5px、KPI 数字 16–17px —— 这是这套方向的核心赌注，也是它的主要风险（见 09 反对意见 02）。

### 5.4 登录页构思（`#login`，460px 左表单 + 1fr 右"产品界面切片"）

- 左侧：品牌标记 `DS` + 一句话定位「AI 市场行情智能分析平台 · 本地单进程」，小标题 `SECURE SESSION`，标题「登录你的分析控制台」，说明「上传市场数据 → 用自然语言提问 → 真实计算 + 图表 + 可逐条核对的报告。账号与会话都留在本机，出口只有一个：这台机器。」
- 两个字段带**真实规则提示**（取自 `app/schemas_auth.py`）：「3–32 位，以字母或数字开头，可用字母、数字、下划线、点、连字符」「至少 8 位，且必须同时包含字母和数字」。
- 错误态用一行红框：「用户名或密码不正确 —— 服务端对『用户名不存在』和『密码错误』返回同一句话，避免账号枚举」。**这个措辞是设计的一部分**：它把安全决定解释给用户，而不是假装那是个 bug。
- 主按钮「登录」+ 次按钮「创建第一个管理员 →」（对应 `needs_bootstrap=true`）。
- 底部脚注：「连续失败会触发限流，直到服务端放行（HTTP 429 + Retry-After）。账号库为空时，登录页自动切换成「创建第一个管理员」—— 系统里没有预置的默认账号。」「会话保存为 HttpOnly Cookie，前端拿不到 token 原文。实例自检 `/api/health` · 登录状态 `GET /api/auth/me`」。
- **右侧不是装饰插画，是"产品界面切片"**（标题就写「PRODUCT SLICE · 真实界面构件，非装饰插画」）：上半部是六阶段横条（06 校验数字标"待执行"）、数据行数/字段数、完全重复的行、存在缺失的字段；下半部是归档库最近 3 条记录与状态分布。右下角一行小字回答"为什么右栏是界面而不是插画"：「登录页要立刻回答『我会得到什么』」。

### 5.5 Dashboard 构思（`#dashboard`，244px 侧栏 + 顶栏 + 3 栏）

- 顶栏：面包屑「工作台 / Market Intelligence Workspace」+ 三个状态徽章（本地单进程 / 已配置大模型 / 接口文档）+ 当前用户 `ops.analyst`。
- **上传内联成一条 strip**，不再是首屏最大的卡片：「点击选择文件，或把文件拖到这里」+ 规则说明 + `已上传: sales.csv · 2,168 行 × 9 列 · dataset_id 90d64c90…9a6` + 「上传」「进入市场分析」。
- 三栏：**左 300px = 数据体检**（数据行数/字段数/文件大小/画像内存 四读数 + 完全重复的行 8 + 存在缺失的字段 5 + 缺失值逐列读数表 + 口径提示块）；**中 1fr = 图表 + 流水线 + 工具**（柱状图内联 SVG、图注写明数值请以报告正文为准、六阶段条、"本次调用的工具"表把未命中的 5 个也列出来）；**右 268px = 读数墙**（六地区合计 77,734,878 大数字、最近分析任务 5 条带状态标签、归档库状态分布条 475/1、大数字预览表）。
- 这套结构直接回应 P1（无空洞）、P6（口径常驻）、P10（未命中工具常驻）。

### 5.6 分析工作区构思

工作区就是"提问 + 六阶段条 + 工具命中表"三件东西共享一屏：用户输入的每个问题，下面立刻看到这次命中了哪几个工具、哪个阶段产出什么。它不返回"对话气泡"，而是返回**一次可核对的计算记录**。

### 5.7 数据可视化构思

- 不追求图表美观，追求"图和数在同一个视口内"：柱状图横向压到 3 栏中间列，数值直标在柱顶（9.5px，颜色比 KPI 数字暗一档，不抢读数）。
- 纵轴保留真实图的 `1e7` 缩放标记与 `销售额_sum` 标签（**不美化掉真实产物的粗糙处**，因为那正是"可核对"的证明）。
- 图注明确写：数值请以报告正文表格里的原值为准，完整分组名见报告正文 —— 把"图是摘要、表是真相"讲清楚。

### 5.8 交互特点

导航用**左侧 2px 竖线**表示当前位置（不用背景块）；表格行悬停整行提亮；状态徽章用 10px 等宽字；所有可点元素都保持 2px 圆角与 1px 边框，**没有一个"漂浮的按钮"**。

### 5.9 优点与风险

**优点**：单位面积信息量三套中最高；口径与来源标注最完整；状态（成功/警告）视觉权重正确；跨页面切换时版式不跳动；对 P1/P3/P6/P7/P8/P10 都有直接回应。

**风险**：
1. **字号偏小**：正文 11.5px、说明 10.5px。在 1440px 窗口下可用，在 1280px 笔记本或缩放 125% 的屏幕上会明显吃力。这是密度纪律的代价。
2. **深色底 + 高密度**：连续阅读报告的体验不如浅色方案；用户从报告页切回工作台会有亮度跳变。
3. 三栏在 1440px 下每栏 268–300px，**再窄就会被压**，没有为 1280px 做降级（原型范围内可接受，落地前必须补）。

## 06 方向 B：研究简报（Research Brief）

**文件**：`D:\个人项目01\ai-data-analyst-agent\.tmp\design3\direction-B.html`
**截图**：`shots\B-login.png`（1440×1331，107,001 B）、`shots\B-dashboard.png`（1440×2448，312,598 B）

### 6.1 设计理念

把这个系统当成**一份要给人看、要被人挑错的分析稿**。分析稿的伦理是"每一个结论后面必须站着一个可核对的出处"，所以版面从上到下就是一条论证链：结论 → 证据 → 数据质量 → 过程 → 归档。它反过来反对"卡片墙"：多张卡片并列会暗示这些信息同等重要，而一篇分析稿必须有权重。

### 6.2 品牌视觉方向

- 纸白 `#faf7f1`（暖白，不是纯白）配墨色 `#1d2530`，细横线 `#ddd6c9`，双线 `#c9c0ae` 做文档头尾。
- **唯一强调色酒红 `#8a2436`**，只出现在：编号 `01–06`、`kicker`、引用块左边线、"结论文本"里的两个大数字、负数差值。一个强调色意味着用户永远知道"红色=重点"，不会疲劳。
- 数据辅助色深青 `#1f5d63`（实测 7.00:1）只用于条形填充与工具名 chip。
- 圆角 1–2px，几乎直角；无阴影；页码/时间/编号一律等宽字。

**实测修正记录**：条形图的次色原来是 `#7d9ea1`，对纸白只有 **2.70:1**（不达标），改成 `#4d7478`（**4.81:1**）。改完之后我发现了更深的问题：主色与次色的对比只有 **1.46:1**，**"第一名"这个信息实际上完全靠颜色承载**。于是又加了一道不依赖颜色的线索 —— 第一名的地区名与数值加粗（`.toprank`），并在 CSS 注释里写明原因。这个修正过程本身就是这个方向的性格：它的每一个视觉决定都要能被追问"凭什么"。

### 6.3 色彩与字体

令牌见 `direction-B.html:12-27`。字体栈：正文 `Segoe UI → Microsoft YaHei → DengXian`；标题 `Songti SC → SimSun → 宋体 → Georgia`（**注意：本机没有思源宋体/Noto Serif CJK，实测只有 simsun.ttc，所以衬线最终会落到宋体**，见 11.4 决策项）；数字 `Cascadia Mono → Consolas`。正文 14.5px / 行高 1.75，是三套里最好读的。

### 6.4 登录页构思（430px 居中窄表单 + 编号"真实状态"清单）

- 文档头风格：左侧 `AI MARKET INTELLIGENCE STUDIO`，右侧「本地单进程」。
- 衬线大标题「把你的表格交给自己人算清楚」（31px，两行）。
- 说明一段：「上传市场数据 → 用自然语言提问 → 真实计算 + 图表 + 可逐条核对的报告。六阶段流水线每一步都有可核对的产出，报告里的每个数字都能追回到某一次具体的工具调用。」（这句话在初稿里写的是"每一步产出都能回溯到某一次具体的工具调用"，复查代码后按反对意见 05 改窄 —— 见 09.2）
- 表单是**下划线式输入**（无框），字段下方就是规则提示。
- 错误态不是红块，是**双细线夹一行酒红字**：「用户名或密码不正确 —— 服务端对『用户名不存在』与『密码错误』返回同一句话，登录接口因此不能用来枚举账号。」
- 按钮区：实心「登录」+ 描边「创建第一个管理员」+ 一行说明「连续失败会被限流，直到服务端放行」。
- **下半页是最特别的部分**：标题「这个系统当前的真实状态（不是宣传语）」，四条编号事实 —— 01 示例数据集 `sales.csv`：2,168 行 × 9 列，137.7 KB，其中 8 行完全重复、5 列存在缺失值（标注来源 `row_count / column_count / memory_bytes`）；02 六阶段流水线可逐段核对（标注"最后一次运行核对了 20 个数字，来自报告校验环节的真实产出文案"）；03 归档库现有 476 条记录（475 SUCCESS / 1 SUCCESS_WITH_WARNINGS），存在 SQLite 里，重启服务后仍在（标注 `workflow_history` 表实测计数）；04 Agent 手上只有 7 个真实工具，算不出来的问题它会说算不出来（标注"来自工具注册表实测"）。
- **设计意图**：登录页不讲"我们能做什么"，而是先证明"我们没说假话"。这是三套里唯一一个把"可信"当作首屏主题的方向。

### 6.5 Dashboard 构思（6 个编号小节，820px 文档流）

- 文档头：左「AI Market Intelligence Studio」+ 定位句，右「数据源 sales.csv · 2,168 行 × 9 列 / 报告编号 e1deda4b · 工作流 40ac2708 / 生成于 2026-10-16 00:23:19 UTC」。
- **sticky 标签栏**（工作台 / 数据集 / 市场分析 / 分析报告 / 历史任务 / 设置（只读））+ 右侧 `ops.analyst · 本地单进程 · 已配置大模型`。滚动时它吸顶，替代侧栏 —— 因为文档流里不需要常驻导航。
- `01 结论 / FINDING`：衬线标题「华南一地的销售额，接近西北的三倍」，正文给出 3.11 倍与 3.15 倍的差别解释（"这个落差不是少数大单撑起来的"），然后用 3px 酒红左边线 + 34px 大数字呈现 `24,871,657.00 / 7,989,816.00`，下面一行小字标明「华南 / 西北　六地区合计 77,734,878.00　来源：任务 T1（group_aggregate）」。
- `02 证据链`：两条证据 T1 / T2，每条写清工具名、口径、引用的正文位置、`cites: T1`；第三条是「本次未命中另外 5 个工具」并逐个列出名字，注明"未命中也要列出来 —— 否则用户不知道还能问什么"。
- `03 六个地区的销售额排行`：**一张宽表解决**左列 sum、右两列 mean 与"与平均水平差值"，条形长度按与华南的比值绘制；表下注明"条形长度按 sum 与华南的比值绘制，不是独立刻度；数值与报告正文表格一致"。
- `04 先说清楚这份数据的三个毛病`：把报告里的"数据质量说明"原文引用进灰底块（检测到 8 行完全重复、5 列存在缺失值、逐列缺失计数），然后正面讲口径差异：「画像里的数据行数 = 2,168（原始行数），而报告的数据质量说明里写的是『去重后还剩 2160 行』。2,168 与 2,160 都对，但口径不同 —— 界面上必须分别标注来源，否则读者会以为其中一个是错的。」
- `05 这次运行经过了什么`：六阶段编号清单，每行是「编号 + 阶段名 + 一句真实产出（含工具名与文件尺寸）+（构图示意 x.xs）」，并在引言里一次讲清「括号内的耗时是**构图示意（非实测数据）**，阶段名、工具名与产出文案是真实的」。
- `06 归档库里已经有 476 条记录`：按问题聚合的排行表（364 / 90 / 10 / 7 / 2），每行给"最近一条"的 `workflow id 前 8 位 · 月-日 时:分`，表下给状态分布与时间口径（"表内时间为 2026-10-16 UTC 的日/时:分"）。
- 页脚「数字来源声明」：本页所有销售额、均值、差值与缺失计数均由服务端工具在同一次工作流（40ac2708）内计算，无人工修改；归档条数与状态分布来自 `workflow_history` 表实测计数。

### 6.6 分析工作区构思

工作区在这套方向里退化成"文档头里的一个输入框 + 生成一篇稿"。它主张：用户要的不是"操作界面"，是"一篇能读的东西"。提问 = 选题，六阶段 = 采编过程（收进 05 节），报告 = 成稿。

### 6.7 数据可视化构思

**不画图**（这是最激进的一条决定）。用"三列表 + 条形长度"代替柱状图：因为这张表能同时承载 sum（大小）、mean（强度）、与平均水平的差值（结构），而柱状图只能承载一个。条形长度用 CSS 宽度百分比（100% / 63.9% / 46.5% / 36.0% / 34.0% / 32.1%），**全部由真实数值算出**。代价：失去了"一眼看出分布形状"的能力。

### 6.8 交互特点

没有卡片，只有横线与编号；sticky 标签栏替代侧栏；表格右侧列全部右对齐等宽数字；负数差值单独用酒红（`−4,160.22` 等，用真正的减号 U+2212 而不是连字符）。

### 6.9 优点与风险

**优点**：可读性最好（正文 14.5px/1.75）；论证链最完整，每个数字都有出处；口径差异讲得最清楚（P6 的正解）；对 P4 重复表格的解法最彻底（合并成一张宽表）；登录页的"用事实代替宣传语"是三套里最可信的开场。

**风险**：
1. **与"工作台"的产品定位冲突**：这套方向适合"读一份报告"，不适合"连续问 20 个问题"。每问一次就生成一篇新稿，用户会淹没在自己的稿子里。
2. **首屏没有操作入口**：结论在最上面，输入框在文档头里，**用户要先往下读完才知道能做什么**。
3. **不画图**是产品层面的赌博：市场行情分析的用户预期里，图是刚需。
4. 单栏 820px 在 1440px 屏幕上左右各留 310px 空白，**屏幕利用率只有 57%**。

## 07 方向 C：智能体驾驶舱（Agent Cockpit）

**文件**：`D:\个人项目01\ai-data-analyst-agent\.tmp\design3\direction-C.html`
**截图**：`shots\C-login.png`（1440×900，227,575 B）、`shots\C-dashboard.png`（1440×1475，222,165 B）

### 7.1 设计理念

这个产品最独特的地方不是"它能算数"，而是"它自己算" —— 有六个阶段、七个工具、一个会说"算不出来"的 Agent。所以界面第一性的事实应该是**这个智能体的工作状态**，而不是它的数据表。驾驶舱的伦理是"把自动化过程做成可见的仪表"，让用户对机器的信任来自**看得见的过程**，而不是来自漂亮的结论。

### 7.2 品牌视觉方向

- 底 `#0b0a1a`（近黑的深靛紫，不是纯黑：纯黑会让所有颜色显得脏），卡片 `#171432`。
- 电光青 `#4ff0d0` 是唯一强调色（实测对卡片 **12.44:1**，对画布 **13.71:1**），用于：进行中的阶段点、主按钮、KPI 强调数字、图表柱、命中工具的勾。
- **12–16px 大圆角 + 一处玻璃拟态**（`backdrop-filter:blur(14px)` + `box-shadow:0 22px 50px rgba(0,0,0,.42)`），只用在登录页表单卡上 —— **全文件唯一一处**。这是刻意的自我约束：玻璃效果在深色底上很抓眼，所以只允许出现在"还没有任何数据要读"的那一屏。
- 一个 46px 的呼吸点动画表示"进行中"，**只在有真实进行中状态时出现**；没有实测数据的地方（阶段耗时）不画进度条。

**实测修正记录**：弱文字原为 `#7c76a3`，对卡片 `#171432` 只有 **4.21:1**（10–11px 小字不达标），改成 `#8b85b3` → **5.16:1**（对画布 5.69:1）。正文 `#f2effc` 对画布 **17.27:1**，是三套里最高的。

### 7.3 色彩与字体

令牌见 `direction-C.html:12-28`。字体栈：`Segoe UI → Microsoft YaHei → DengXian`；数字 `Cascadia Mono → Consolas`。字号分布最大：正文 12–13.5px，卡片标题 14.5px，**KPI 数字 30–34px**，登录页品牌标题 52px。

### 7.4 登录页构思（60% 电影感品牌区 + 40% 玻璃表单卡）

- 左侧 60%：品牌标记 + 一句话定位；一枚胶囊徽章「六阶段流水线 · 报告里每个数字都能追回工具调用」（初稿写的是"每一步都可回溯"，按反对意见 05 改窄）；52px 两行大标题「**它先算数，再写报告。**」（"算数"用青色，读起来像重音）；一段说明「上传市场数据 → 用自然语言提问 → 真实计算 + 图表 + 可逐条核对的报告。报告里每个数字都能点回到某一次工具调用，模型不许凭空写数。」
- **三个事实数字横排**（不是形容词）：`2,168 × 9`（示例数据集 sales.csv · 137.7 KB）、`476`（归档记录 · SQLite 持久化，重启仍在）、`7`（真实工具 · 算不出来就说算不出来）。
- 左下角一行技术事实：`GET /api/auth/me`　`/api/health`　会话：HttpOnly Cookie。
- 右侧 40%：玻璃卡。标题「欢迎回来」，副标题「登录你的分析驾驶舱」。两个字段 + 真实规则提示。错误态是粉红细框 + 一行说明「用户名或密码不正确 —— 服务端不区分『用户名不存在』和『密码错误』，避免账号枚举」。主按钮青色「登录」，次按钮描边「创建第一个管理员（账号库为空时）」。
- 卡底三行小字把系统真实行为讲透：「连续失败会被限流；这个部署没有任何预置账号，第一个管理员由人在首次部署时设定。改密码会踢掉该账号的全部会话，并为当前设备重新签发。」
- **构图说明**：这是三套里唯一一张 900px 高度内既有品牌主张、又有三个硬事实、又有完整表单与规则说明的登录页。

### 7.5 Dashboard 构思（76px 窄轨 + KPI 行 + 卡片拼版）

- **76px 图标窄轨**：`DS` 标记 + 6 个图标（工作台/数据集/分析/报告/历史/设置）+ 底部 `OA` 用户圆标。图标下只有 10px 中文标签，不做二级展开 —— 这是对 P5 的回应：把"去处"压缩到一列，把"过程"归还给主区。
- 顶栏：标题「市场分析驾驶舱」+ 状态行「本地单进程 · 已配置大模型 · ops.analyst · workflow 40ac2708」+ 右侧**提问框**（placeholder「问点什么 —— 例如「各地区的销售额对比」」+ `⌘K` + 青色「开始分析」按钮）—— **这是三套里唯一把提问框放在首屏顶部的**，直接回应 06.9 里 B 的"首屏没有操作入口"。
- **KPI 行 4 张卡**：数据规模 `2,168 × 9`（sales.csv · 137.7 KB）、六地区销售额合计 `77,734,878`（来自任务 T1，6 行求和）、最高地区 `24,871,657`（华南，是西北的 3.11 倍）、归档记录 `476`（分支：364 条同一问题）。
- 主区 `board`：**左 392px = 智能体执行 · 六阶段纵向时间线**（已完成阶段实心青点、进行中阶段呼吸点 + 「撰写报告 进行中」徽章、待执行阶段空心点 + "等待执行 —— 上一次运行在这一步核对了 28 个数字"）；每条包含阶段名 + 一句真实产出 + **这次命中的工具徽章**（`group_aggregate → T1`、`compare_groups → T2`），再加一行 7 个小徽章把**未命中的 5 个工具灰显列出**，并注明「灰色徽章是本次未命中的工具 —— 也显示出来，用户才知道还能问什么」。**右 1fr = `.rcol` 纵向排两张卡**：大图表卡（柱状图 + 底栏"数据来源 任务 T1 / group_aggregate · 纵轴 销售额_sum · 横轴 地区 · 图表文件 960 × 576 PNG（服务端 matplotlib）"）+ 数据体检卡（4 条 mini 读数条 + 2 条质量警告 + 1 条口径提醒）。
- row2：左 = 最近分析任务（5 条，状态徽章右对齐成列，底部「364 / 476 条是同一个问题 / 历史需要筛选，不该平铺」）；右 = 「这次命中的工具 / 没命中的工具」完整清单（7 个工具的**真实一句话说明**，命中的带勾、没命中的灰显）。

### 7.6 分析工作区构思

工作区的中心是"**时间线 + 提问框**"：上面能直接提问，左侧实时显示智能体正在做第几步，右侧同步显示这一步产出的图和读数。用户不需要等整条流水线跑完才看到东西。产出物永远和产出它的那一步在同一屏。

### 7.7 数据可视化构思

- 图表卡是主区最大的一块（720px 高），柱体用青色 `#3fd6b4`（实测对卡片 9.93:1），数值直标在柱顶。
- 图表卡底部有一整行**来源脚注**（数据来源 / 纵轴 / 横轴 / 图表文件），把"这张图是谁算出来的"钉在图的旁边，而不是塞在正文里。
- 数据体检不用数字堆，用**迷你读数条**（`数据行数 2,168 行`、`字段数 9 列`、`文件大小 137.7 KB`、`画像内存 228.7 KB`）—— 让"量级"可被眼睛比较，而不仅是被读到。

### 7.8 交互特点

呼吸点只表示真实"进行中"；阶段可展开（原型里用视觉层级暗示而非真实交互）；工具徽章命中/未命中用**颜色 + 勾号/灰显**双通道；历史行状态徽章右对齐成列（扫一屏就知道哪条有问题）。

### 7.9 优点与风险

**优点**：首屏是唯一同时具备"品牌陈述 + 4 个真实 KPI + 提问入口 + 智能体过程"的构图；对 P2（历史按状态成列）、P5（窄轨导航）、P7（失败有形态）、P10（未命中工具）都有直接回应；视觉完成度最高，最像"一个产品"。

**风险**：
1. **装饰成本最高**：圆角、玻璃、发光点、阴影都是"需要维护的视觉债"。如果后续要加 20 个页面，这套语言会迅速失控。
2. **青色大数字 + 深底**在长时间盯屏时会产生视觉疲劳（虽然对比度实测达标，但饱和度偏高）。
3. **信息密度低于 A**：KPI 卡每张只放一个数字，392px 的时间线栏在数据多时会显得空。
4. 玻璃拟态在**低端设备/远程桌面上可能掉帧**（`backdrop-filter` 是真实渲染成本）。

## 09 交叉评审意见（含反对意见）

本节按交叉评审要求写。**反对意见单列，且不是走过场** —— 第 09.2 节里每一条都指向具体的截图区域或代码事实，可以被反驳、也可以被采纳。

### 09.1 对三套方向的共同批评

1. **三套都只画了"有数据之后"的状态。** 空状态（上传前）、加载中、上传失败、大模型未配置、限流 429 —— 这五种状态在三套原型里只有零散暗示（A 的登录页有错误态、C 的时间线有"待执行"）。这是原型阶段的合理取舍，但**落地时必须补**，否则会重演现在"界面表达了系统没有的状态"的反向错误。
2. **三套都没有解决"数据集持久化"这个真正的难题。** A/C 画了"当前数据集"芯片，B 在文档头写"数据源 sales.csv"。这些视觉元素全都依赖一个**目前不存在的接口**（`GET /api/datasets` 没有）。视觉上把不存在的功能画出来，就是"假数据"的另一种形式。我把它明确列为决策项（11.4），而不是偷偷画完就算。
3. **KPI 数字的"合计 77,734,878"在三套里都被当作首屏主角之一**，但它其实是"六个地区求和"，业务上信息量有限（用户更关心排名与差距）。这是三套共有的**选题偏差**：因为我们手上只有这一份示例数据，容易把"数据里有什么"误当成"用户想看什么"。

### 09.2 反对意见（必须有的部分）

**反对意见 01 —— 反对"以 C 为主"的视觉语言整套照搬。**
C 的圆角 12–16px + 玻璃 + 发光点 + 阴影，在**登录页**是资产，在**工作台**是负债。理由有实测支撑：C 的每张 KPI 卡是 `padding:14px 16px` + `border-radius:14px`，卡片本身的内边距与外圆角吃掉了约 15% 的卡片面积；而 A 的同样位置用 1px 分隔线，同样的 4 个读数只用 300px 宽就装下了。**主张：C 的"外层气质"（深靛紫底、电光青强调、大字号 KPI）保留，但工作台内部的卡片必须降级为 A 的线框语言**（圆角 ≤6px、去掉阴影与发光、用线分隔）。这其实就是 Lead 说的"融合 A 的密度纪律"，但我要把话说得更硬：**不是"融合"，是"必须换掉"**。

**反对意见 02 —— 反对把 A 的"小字号换密度"当作正面经验继承。**
Lead 的结论说"融合 A 的密度纪律"。我同意纪律，但**不同意连字号一起继承**。A 的说明文字 10.5px、正文 11.5px。在 1440×900 的截图里它清晰，但那是因为 Chromium 渲染在 1x 缩放下截图；真实的项目用户里，只要有人用 125% 系统缩放（Windows 笔记本默认就是 125% 或 150%），10.5px 就会退化成难读的灰点。**主张：密度纪律继承，字号底线不继承 —— 正文不得低于 12.5px，说明文字不得低于 11.5px。** 这会让 A 的结构在同样的 1440px 宽度下多占约 8% 的高度，可接受。

**反对意见 03 —— 反对"智能体透明度"只做成一个时间线组件。**
Lead 的结论说"融合 B 的智能体透明度"。但 B 的透明度**不是组件，是叙述方式**：它把 T1/T2 的引用、未命中的 5 个工具、以及"这次核对了 20 个数字"都写成正文句子，读者是被"讲"服的。C 目前的透明度是一个视觉时间线 + 工具徽章，用户是被"展示"的。两者不等价。**主张：C 的时间线保留（它是首屏最强的视觉锚点），但必须在时间线下面补一段 B 式的**自然语言证据句**，例如"这一步用了 `group_aggregate`，对『地区』分组求和，返回 6 行；报告里出现的 24,871,657.00 就是这 6 行里的第一行"。** 少了这句话，时间线只是好看的进度显示。

**反对意见 04 —— 反对"B 只是备选"这个定位。**
B 在"数据可信度传递"和"可读性"两项上都是 5 分，且它是唯一正面处理"2,168 vs 2,160 口径差"的方向。这个能力不该被降级成"备选方案"，而应该被**提取成一个可复用的页面模式**：报告阅读页。**主张：最终产品应该是"C 做工作台/驾驶舱 + B 做报告阅读页"的双形态，而不是"C 通吃所有页面"。** 这条比 Lead 当前的结论更强，我有原型支撑：B 的 05 节（六阶段编号清单 + 括号标注示意）和 C 的时间线是同一个信息的两种正确形态 —— 一个给"读者"（要读完、要引用），一个给"操作者"（要看进度）；把它们合并成一种，就会丢掉一半用户。

**反对意见 05 —— 反对在 UI 里承诺"每一步都可回溯"，除非后端补上归档详情接口。**
这句话在三套原型里出现过两次（grep 实测，不是印象）：
- 方向 B 的登录页说明：「六阶段流水线的每一步产出，都能回溯到某一次具体的工具调用」（`direction-B.html:157`）；
- 方向 C 的登录页徽章：「六阶段流水线 · 每一步都可回溯」（原 `direction-C.html`，**已按本条意见改写为「六阶段流水线 · 报告里每个数字都能追回工具调用」**）。
（修正说明：我初稿写的是"方向 A 也写了这句"，复查 `grep 回溯 .tmp/design3/*.html` 后确认 A 里没有这句，已更正。）

但代码实测只支持**较窄的那个说法**：`app/schemas_workflow.py:175` 写明校验 Agent"是『报告里的数字能核对』这句话的实现"，`app/agents/validation.py:701` 的 `_check_report_numbers`（"核对报告里的数字与列名，返回一份校验结果（**完全不调大模型**）"）把报告里的数字逐条对回工具结果 —— 所以"**报告里每个数字可回溯到工具调用**"成立；而"**每个阶段都可回溯**"不成立：`app/web/app.js:1595 openHistoryDetail(workflow_id)` 只把归档渲染成 `table.kv` 键值表，不展示任何阶段的产出。**方向 B 的这句措辞也应当同样改窄。**

## 10 不采用的做法清单

以下做法我在三套原型里**都没有用**，并说明为什么。这份清单同样是对实现者的约束。

### 10.1 参考站点类（无法访问 / 无法验证的做法）

### 10.2 视觉技法类

| 不采用 | 原因 |

| 装饰性渐变（背景径向光晕、按钮渐变、文字渐变） | 与"数字可信"冲突：渐变让用户难以判断哪里是真实数据的边界。C 的深靛紫底是**纯色**，唯一的一点光晕出现在登录页品牌区且不用来承载信息 |
| 装饰性阴影（卡片浮起、多层投影） | A/B 零阴影；C 只在登录页表单卡用一处阴影（`0 22px 50px rgba(0,0,0,.42)`），因为它必须把"表单"从"品牌区"里抬出来。**工作台内不允许出现阴影** |

| 卡片机械重复 | 现在报告页同一张表渲染三遍就是这个问题（P4）。**同构卡片连续超过 3 张就必须换成表格/列表/线框** |

| 无意义的图标描边与装饰线 | A 用 1px 线做**功能分隔**；不做"为了好看"的竖线、角标、斜纹 |

### 10.3 信息表达类

| 不采用 | 原因 |
| --- | --- |
| 把 `workflow_id`（32 位 hex）、`dataset_id`（全文）、ISO 微秒时间戳当正文展示 | 它们是**内部标识**。展示规则：默认只给前 8 位（如 `40ac2708`）、时间到分钟、需要时点开复制。C 的 `40ac2708 · 2026-10-16T00:23:19` 是原型里最长的形式，落地时应收成 `10-16 00:23` |

## 11 最终推荐方向与理由

Lead 已定：**方案 C 为主 + 融合 A 的密度纪律与 B 的智能体透明度**。我的结论是：**部分支持，但要加三个附加条件 + 提出一个更强的主张。**

### 11.1 支持的部分（有原型证据）

1. **C 做骨架是对的，证据是信息架构而不是好看**：C 是唯一在首屏同时容纳「品牌陈述 + 4 个真实 KPI + 提问入口 + 智能体过程」的构图。实测它的登录页在 1440×900 内既有 52px 品牌标题、又有 3 个硬事实、又有完整表单与认证规则说明；A 和 B 的登录页加起来覆盖的信息量与之相当，但都没有在同一屏完成。
2. **C 的强调色在实测中最稳**：电光青对卡片 12.44:1、对画布 13.71:1，而且它**只用一个强调色**，比 A 的"青 + 钢蓝 + 橙 + 绿 + 红"更容易保持一致性。
3. **C 的窄轨导航直接解决了 P5**：76px 的图标轨把"去处"压到最小，把主区让给"过程"，这是正确的主次关系。
4. **A 的密度纪律确实必须融合**，而且理由很具体：现在的报告页高度 2,717px、B 的仪表盘 2,448px，而 C 只有 1,475px —— 但 C 的 1,475px 里还有约 15% 被卡片内边距与外圆角吃掉。融合 A 的线框语言能把这 15% 还给内容。

### 11.2 需要追加的三个条件

- **条件一（来自反对意见 01）**：C 的"外层气质"保留，**工作台内部的卡片必须换成 A 的线框语言**（大面块圆角走 `--r-md`/`--r-lg` 令牌、零阴影、1px 分隔线；胶囊用 `--r-pill`）。
- **条件二（来自反对意见 02）**：密度纪律继承，**字号底线不继承** —— 正文 ≥12.5px、说明 ≥11.5px。
- **条件三（来自反对意见 03）**：时间线下面必须补一句 B 式的自然语言证据句，否则"智能体透明度"只是装饰。

### 11.3 我的更强主张

**不要把 C 通吃到所有页面。** 建议采用双形态：

| 形态 | 页面 | 依据 |
| --- | --- | --- |
| **C 形态（驾驶舱）** | 登录页、工作台、分析工作区、历史页 | 这些页面的用户是"操作者"，要的是状态与入口 |
| **B 形态（简报）** | 报告阅读页、归档详情页 | 这些页面的用户是"读者"，要的是论证与引用 |

理由（有原型与观察支撑）：B 的仪表盘 2,448px 高、屏幕利用率 57%，作为"工作台"是失败的；但作为**报告**它是三套里最好的 —— 它的 01–06 编号结构就是报告的天然骨架，它把数据质量问题提升为独立小节（04），它每个数字都有 `cites: T1` 出处。而 C 的 1,475px 工作台如果在报告页复用，那张 960×576 的图 + 报告正文会被塞进卡片，重复现在 `03-workflow-done.png` 的"图和正文分离"问题。**同一个产品里，操作界面和阅读界面本来就应该是两种形态**；硬要统一，代价是两头都不合用。

如果 Lead 只接受单一形态，那么**退让方案**是：C 的骨架 + A 的线框密度 + B 在报告页内的 01–06 编号小节与引用脚注（即把 B 的"论证结构"移植进 C 的卡片里，但放弃 B 的单栏文档流与 14.5px 大行高）。这个退让方案我也有原型可以支撑：C 的仪表盘里，"数据体检"卡底部的口径提醒、图表卡的来源脚注行，本来就是 B 那些形制的移植。

#### D1 报告页双形态：**通过**（本次最重要的决定）

| 页面组 | 采用 | 具体语言 |
| --- | --- | --- |
| 操作者页面：登录、工作台、市场分析、历史 | 方向 C 的外层气质 + **方向 A 的线框语言** | 大面块圆角走 `--r-md`（6px）或收窄后的 `--r-lg`、零阴影、1px 分隔线、密度纪律（信息优先）；胶囊只用 `--r-pill` |
| 阅读页面：报告阅读页、归档详情页 | 方向 B 的**阅读语言** | 报告正文 measure = `var(--ds-measure-report)`（当前 78ch，见 `app/web/tokens.css:283`）、编号小节、证据脚注、悬挂缩进 |

**理由（Lead）**：任务书第 6.2 节明确要求"每个页面按主要任务选择结构，不要所有页面强制同一布局"，而报告是阅读场景 —— 阅读要靠行宽、节奏、脚注，不靠多栏卡片。

**附带边界（同样是定案，不是建议）**：**B 的独立视觉语言不采纳。**
- 不换衬线字体（与 D5 一致）；
- 不引入酒红 `#8a2436`（统一品牌色由 `app/web/tokens.css` 承载）；
- 不用 820px 单栏替换全站栅格 —— 报告页只改**版式节奏**，不改品牌色与字体族。

这同时接受了 11.2 的三条条件：① C 外层 + A 线框；② 继承 A 的密度纪律但**不继承它的 11.5px 字号底线**（正文 ≥ 12.5px、说明 ≥ 11.5px）；③ 六阶段时间线下面必须补一句 B 式自然语言证据句。

#### D2 数据集列表接口：**做**（原型里的"当前数据集"芯片保留，不要删）

- 落地任务：task-11（backend-tests）—— `GET /api/datasets` + 数据集/归档的 **owner 隔离**（别人的资源一律 404，不返回 403，避免泄露"存在但无权"）。
- 截至本文定稿，`app/api/routes_datasets.py` 只有 `POST /datasets/upload`、`GET /datasets/{id}`、`GET /datasets/{id}/profile` 三条；**列表接口尚未出现在代码里**，以 task-11 的完成结果为准（见 ux-spec-final 附录 A）。
- 原型影响：A/C 的"当前数据集"芯片、以及刷新页面后恢复 dataset_id 的能力，都依赖这一条。

#### D3 深链接：**做**（9 条路由，归 task-12 / frontend-engineer）

`#/workbench`、`#/dataset`、`#/dataset/{dataset_id}`、`#/analysis`、`#/report`、`#/report/{workflow_id}`、`#/history`、`#/history/{workflow_id}`、`#/settings`。

**失效 id 的行为是硬规定**：显示**真实错误态**（404 就写"这条记录不存在，或将当前账号无权访问"），**不许静默回落到列表页**。依据：`GET /api/workflows/history/{workflow_id}` 查不到就是 404（`app/api/routes_workflows.py:291` 的注释写明"§8.3.1 禁止 fallback 复活"），前端静默回落会让"我点的那条怎么没了"变成一个查不出来的故障。
**补充事实（实现方必须知道）**：现有前端 `viewFromHash()` 只认三种视图，且 `app/web/app.js:416 currentTarget()` 已经在登录跳转时带上了 `pathname + search + hash` —— 深链接的"回跳"能力前端已经有一半，缺的是路由表本身。

#### D4 登录页与首次部署状态：**在做**（task-13 / login-page 队友）

包含空库时的 `needs_bootstrap` 首次部署模式（`GET /api/auth/me` 的 `needs_bootstrap=true` → 显示"创建第一个管理员"，`POST /api/auth/bootstrap` 只在账号库为空时可用；**不预置默认账号/默认密码**）。

**与 11.4 原始设想的一处修正（实测）**：Lead 消息里写的"未登录跳 `/login?next=`"在**服务端当前不存在**这条实现 ——
- `app/main.py:347` 的 `GET /login` 只是返回静态 `login.html`（不读 `next`）；
- `app/main.py:386-389` 的 docstring 明确写着"**为什么把 `next` 参数省掉**：回跳地址一旦由查询串决定，就得防开放重定向，这个应用只有一个主页面，登录成功固定回 `/app`"；
- 前端 `app/web/app.js:413-418` 的注释则把 `pathname + search + hash`（含 `#/report/{id}`）拼成了 `next` 并保存。
所以：**跳转本身由服务端 303 决定（`GET /app` 未登录 → 303 `/login`），回跳由前端读 `next` 完成，且必须校验 `next` 是站内路径**（同源、以 `/app` 开头）才允许跳，否则就落回 `#/workbench`。这条修正已写进 ux-spec-final 的 §1 与流程 ②。

#### D5 不使用衬线字体

**理由（我提供的实测依据，Lead 采纳）**：本机字体目录实测只有 `simsun.ttc`（宋体）/ `simhei.ttf`（黑体）/ `msyh.ttc`、`msyhbd.ttc`（微软雅黑）/ `Deng.ttf`、`Dengb.ttf`（等线），**没有思源宋体 / Noto Serif CJK**，B 的衬线标题最终只会落到 Windows 宋体，小字号下质量不可接受。
**替代手段**：报告页的辨识度用**版式**建立 —— 窄行宽（`var(--ds-measure-report)`，当前 78ch，见 `app/web/tokens.css:283`）、编号小节、证据脚注（`cites: T1`）、数字右对齐等宽（`tabular-nums`）。字体栈最终简化为"微软雅黑 + 等宽"两族。

#### D6 六阶段耗时：**当前禁止显示**

**理由（Lead 核实）**：`app/schemas_workflow.py` 的 `WorkflowState` 只有工作流级 `created_at` / `started_at` / `finished_at`，**没有阶段级时间戳**，所以任何"阶段耗时"都是编造。
**规则**：
1. 阶段只显示**真实状态**（`PENDING` / `PROFILING` / `PLANNING` / `EXECUTING` / `CHARTING` / `REPORTING` / `VALIDATING` / `SUCCESS` / `SUCCESS_WITH_WARNINGS` / `FAILED`，来源 `app/schemas_workflow.py:72-81`）；
2. 允许显示**整条任务的真实总耗时**（由上面三个时间戳算出）；
3. UI 必须如实写"阶段级耗时后端暂未提供，需要改后端才能显示"；
4. **待办项**：后端补阶段时间戳（本条登记为待办，见 ux-spec-final 附录 A 第 4 项）。
我原型里 C 的做法（"没有实测数据就不画进度条"）就是这个原则，保持。

#### D7 措辞：采用改窄后的版本

最终措辞：**"报告里的每个数字都能追回到某一次具体的工具调用"**。
依据（我实测的两处源码）：`app/schemas_workflow.py:175`（校验 Agent"是『报告里的数字能核对』这句话的实现"）、`app/agents/validation.py:701`（`_check_report_numbers`：核对报告里的数字与列名，完全不调大模型）。
**不要再用**"每一步都可回溯/每一步产出都能回溯"—— 阶段级回溯后端不提供，归档详情目前只有键值表（`app/web/app.js:1595 openHistoryDetail`）。
