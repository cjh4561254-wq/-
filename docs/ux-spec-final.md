## 0 这份文件怎么用

1. **它是实现清单**：前端按 §2 的格子实现，一格未实现就是一个未完成项。
2. **它是验收对照表**：浏览器验收时逐格点开，看到的呈现必须与格里写的一致；不一致以本文为准，或以"改本文 + 说明理由"结束。
3. **它是独立评审的输入**：评审可以直接引用格子编号，例如"`P3-S5`（市场分析 · 会话失效）不符合"。
4. **编号规则**：页面 `P1`–`P5`（§2.1），状态 `S1`–`S7`（§2.2 定义），格子引用写成 `P3-S5`。路由引用写成 `R1`–`R9`（§1）。

**三条硬规矩**（违反任何一条，这一格就算没做）：

- **不许编造**：每一格写的文案、字段、按钮，都必须对应真实接口或真实页面元素（格子末尾的"依据"列给出接口路径或代码位置）。
- **不许留空格**：不适用的格子必须显式写"不适用 + 原因"，不允许空着让人猜。
- **不许假装**：后端不提供的能力（重试阶段耗时、取消任务、数据集删除、导出报告）一律写"本期不做 + 原因"，不许画一个按不动的按钮充数。

## 1 路由表（9 条）

### 1.1 静态资源与跳转约定（先看这张，否则后面 9 条会看错）

| 路径 | 真实行为（实测） | 依据 |
| --- | --- | --- |
| `GET /` | 返回应用主页面 `app/web/index.html`，**故意不要求登录**（服务端返回 200 不代表能拿到数据） | `app/main.py:326` `root()` 的 docstring |
| `GET /login` | 返回 `app/web/login.html`，匿名可开（否则"登录页要求登录"是死循环）；**不读 `next` 参数** | `app/main.py:347` `login_page()` |
| `GET /app` | 已登录 → `index.html`；未登录 → **303 跳 `/login`**（不是 401 JSON）；docstring 明写"**为什么把 `next` 参数省掉**"（防开放重定向） | `app/main.py:362` `app_page()`、`app/main.py:386-389` |

**回跳怎么做（定案）**：应用内部全部是 `hash` 路由，登录**不会**离开当前文档路径，所以"登录后回到原处"由前端完成，不依赖服务端：
- 发现未登录时，前端把 `window.location.pathname + search + hash`（即 `currentTarget()`，见 `app/web/app.js:416`）记下来；
- 跳 `/login` 时带上它（`location.assign("/login?next=" + encodeURIComponent(target))` 或等价写法）；
- 登录页读 `next` 后**必须校验**：只接受以 `/app` 开头、同源、且不含 `//` 与 `\` 的值；校验不通过就落回 `/app#/workbench`。
- 这是"服务端不提供 `next`"与"用户需要回跳"之间的唯一合法接缝；**不得**为了让回跳生效去改 `/app` 的 303 行为。

### 2.2 七种状态的定义（先定义再填格，避免各页理解不一致）

| # | 状态 | 判定依据（实测接口层面） |
| --- | --- | --- |
| S1 | **Loading** | 请求已发出、还没有结果。首次加载与手动刷新都算 |
| S2 | **Empty** | 请求成功（`ok:true`），但业务上"没有东西可显示"：数据集 0 条、归档 0 条、还没有报告 |
| S3 | **Error** | 有明确失败：HTTP 4xx/5xx、网络中断、服务端 `ok:false` |
| S4 | **Unauthorized** | 尚未登录，或登录了但该资源不属于当前账号（服务端一律 404） |
| S5 | **Session-expired** | 曾经登录着，中途 `GET /api/auth/me` 变 `authenticated:false`，或受保护接口第一次返回 401（`UNAUTHORIZED`） |
| S6 | **Partial-failure** | 整体成功但有局部问题：`SUCCESS_WITH_WARNINGS`、报告中部分段落被丢弃、图表文件读不到、上传成功但画像告警 |
| S7 | **Disabled-because-precondition** | 控件可见但按不动，且**页面必须写出为什么**（禁止只灰不解释） |

## 3 七条关键流程

流程写法：**步骤 → 每步的真实请求 → 用户看到什么 → 出错时走哪一格**。凡带【实测】的是我已经在代码或真实数据里核对过的行为。

### 流程 ① 首次部署（空库 → 建管理员 → 进入应用）

> 涉及路由：`GET /` → `GET /login` →（成功后）`#/workbench`（R1）。页面状态见 P0（§2.8）与 P1（§2.3）。

| 步 | 动作 | 真实请求 | 用户看到 |
| --- | --- | --- | --- |
| 1 | 部署者打开根地址 | `GET /`（不要求登录） | 应用主页面外壳 + 会话门在检查 |
| 2 | 会话门发现未登录 | `GET /api/auth/me` → `{authenticated:false, needs_bootstrap:true}` | 记 `next` → 跳 `/login` |
| 3 | 登录页判断模式 | `GET /api/health` + `GET /api/auth/me` | 切换为**"创建第一个管理员"**模式（不是登录模式），并写明"这个部署没有任何预置账号" |
| 4 | 填写账号 | 无请求（只做本地校验） | 用户名提示"3–32 位，以字母或数字开头，可用字母、数字、下划线、点、连字符"；密码提示"至少 8 位，且必须同时包含字母和数字" |
| 5 | 提交 | `POST /api/auth/bootstrap` | 成功 → `AuthState.authenticated:true` → 按 `next` 回跳（无 `next` 就 `/app#/workbench`） |
| 6 | 失败分支 | — | 账号库已被别人建成 → 服务端拒绝 → 页面**切回登录模式**并说明"这个部署已经有账号了，请直接登录"（不是报"服务器错误"） |
| 7 | 落回工作台 | `GET /api/datasets`、`GET /api/workflows/history?limit=5&offset=0`、`GET /api/health` | P1 的三块各自加载；空库 → 数据集 Empty（P1-S2）、归档 Empty（P1-S2） |

**实测依据**：`GET /api/auth/me` 返回 `AuthState{authenticated, user, needs_bootstrap, session_expires_at}`；`POST /api/auth/bootstrap` 只在账号库为空时允许；`app/main.py:301` 注释写明"认证路由不挂 require_user —— 登录、退出、『我现在是谁』、首次初始化，这四个本来就发生在还没有身份的时候"。

### 流程 ② 日常登录（含 401 / 429 / 5xx 三种失败）

> 涉及路由：`GET /login` →（成功且 `next` 合法）→ `next` 指向的 hash 路由（如 `#/report/{workflow_id}`，R6）。回跳校验规则见 §1.1。

| 步 | 动作 | 真实请求 | 用户看到 |
| --- | --- | --- | --- |
| 1 | 打开 `/login` | `GET /api/health` | 服务状态（登录页唯一能匿名读到的接口，`app/main.py:303-307` 写明了原因） |
| 2 | 判断是否已登录 | `GET /api/auth/me` | `authenticated:true` → 直接回跳并提示"已登录，正在返回…"；`false` → 显示表单 |
| 3 | 提交 | `POST /api/auth/login` | 成功 → `authenticated:true` → 回跳 `next`（校验通过时）或 `#/workbench` |
| 4a | **401** | 服务端固定返回"用户名或密码不正确" | 表单上方错误条显示**同一句话**；**不区分**用户名/密码；输入框保留用户名、清空密码 |
| 4b | **429** | 响应头带 `Retry-After` | "登录尝试过于频繁，请在 N 秒后重试"，提交按钮禁用并倒计时到 0 秒自动恢复 |
| 4c | **5xx** | `ApiResponse.ok=false` + `error.message` | "服务端出错了：<message>" + "重试"；**不吞掉**原始错误码 |
| 5 | 网络中断 | fetch 失败 | "连不上服务，请确认服务已启动" + "重试" |

**实测依据**：`app/errors.py` 的状态码表（401/403/429 分列，`UNAUTHORIZED`/`FORBIDDEN`/`RATE_LIMITED` 三个独立业务码）；`app/api/routes_auth.py:210` 的 `headers={"Retry-After": str(locked_for)}`；`app/main.py:186-188` 说明为什么必须转发响应头。

### 流程 ③ 上传数据集（成功 / 校验失败 / 超限 / 网络中断）

> 涉及路由：R1 `#/workbench`（上传卡）→ 成功后 R3 `#/dataset/{dataset_id}`（详情与画像）。

| 步 | 动作 | 真实请求 | 用户看到 |
| --- | --- | --- | --- |
| 1 | 选文件（也支持拖入） | 无请求 | 文件名 + 大小显示在选择区；**本地先判一次**扩展名（`.csv`/`.xlsx`）与大小 |
| 2 | 点"上传" | `POST /api/datasets/upload`（multipart） | 按钮切加载态并禁用（P1 的 S7 规则）；上传进度用真实 `fetch` 进度事件，**没有进度事件就不显示假进度条** |
| 3a | 成功 | `ok:true` + `Dataset` | ①芯片显示`sales.csv · 2,168 行 × 9 列`；②随后自动请求画像 `GET /api/datasets/{id}/profile` 填 KPI；③若有重复行/缺失列，出现 P1-S6 的琥珀提示条 |
| 3b | 扩展名不支持 | `415 UNSUPPORTED_FILE` | "这个文件类型不支持：只接受 .csv / .xlsx" + **保留已选文件**让用户改选 |
| 3c | 超过大小上限 | `413 FILE_TOO_LARGE`（上限默认 **10 MB**，可配到 200 MB） | "文件太大：上限是 10 MB"（数字来自服务端 message，前端不写死）+ 当前文件实际大小 |
| 3d | 网络中断 | fetch 失败 | "上传中断：文件没有被保存，可以重试" + 重试按钮（**不要**说"上传失败"就完事，用户需要知道不用重新选文件） |
| 4 | 上传成功但画像失败 | `GET /api/datasets/{id}/profile` 失败 | 芯片照常显示（上传确实成功了），KPI 区显示 P1-S3 的分块错误 + 只重拉画像 |

**实测依据**：`app/config.py:78` `max_upload_mb: int = Field(default=10, gt=0, le=200)`；`app/api/routes_datasets.py:69-90`（分块读、超限立刻抛 413、`f"文件太大，上限是 {settings.max_upload_mb} MB"`）；`app/web/app.js:878` 注释写明最常见的就是 `FILE_TOO_LARGE`(413) 与 `UNSUPPORTED_FILE`(415)。

### 流程 ④ 建分析任务（成功 / 重复提交 / 409 / 后台失败）

> 涉及路由：R4 `#/analysis`（提问卡 → 执行面板）。409 在本项目的真实含义见本节末尾说明。

| 步 | 动作 | 真实请求 | 用户看到 |
| --- | --- | --- | --- |
| 1 | 进入市场分析 | 无请求（用已有的 dataset_id） | 上下文行"本次分析使用：sales.csv · 2,168 行 × 9 列"（现有实现 `app/web/app.js:1188`） |
| 2 | 输入问题 | 无请求 | 示例 chip 可一键填入；提交按钮可用性由真实前置条件决定 |
| 3 | 提交 | `POST /api/analysis` → **HTTP 202**（语义是"已受理"，不是"已完成"） | 按钮切加载态并禁用；立刻拿到 `workflow_id`（32 位小写 hex）并跳 `#/analysis`（或就地开始轮询） |
| 4 | 重复提交 | 前端拦截：提交进行中按钮禁用 | **不发第二个请求**；若用户用键盘或脚本绕过，前端在 `state.asking` 为真时直接忽略（现有实现 `app/web/app.js:1218`） |
| 5 | 后台失败 | `GET /api/workflows/{id}` 轮询到 `status=FAILED` | 步骤面板标红该阶段 + 错误码 + 原始 message；`#workflow-error` 显示失败原因；**允许重问，不自动重试**（`RETRYABLE` 目前只有 `SERVICE_UNAVAILABLE`，`app/web/app.js:53`） |
| 6 | 超时 | `error.code = WORKFLOW_TIMEOUT`（**HTTP 仍是 200**） | 明确的超时态："这次分析超时了，结果没出来" + 原因（超时不是崩溃，不要显示"服务器错误"）；允许重试 |
| 7 | 数据集不存在 | `404 NOT_FOUND`："数据集不存在" | 错误条在提问卡内 + 提示"可能是服务重启过，去工作台重新上传"；**用户输入的问题不许丢** |

**实测依据**：`app/api/routes_analysis.py:49-57`（`status_code=202` + docstring 说明"写成默认的 200 会让前端以为结果已经有了"）、`:67-77`（数据集不在内存 → 404，"当场告诉他比让他轮询更省事"）、`:79-81`（`workflow_id` 必须是 `uuid4().hex`，32 位小写无连字符）、`:92-93`（"先登记、再排队"，否则前端会短暂看到 404）；`app/schemas.py:35`（`WORKFLOW_TIMEOUT` 注释："HTTP 仍是 200"）。

**409 说明（不许编造）**：本项目**没有** 409 语义的接口 —— `ErrorCode` 里没有 `CONFLICT`，`app/errors.py` 的状态码表里也没有 409（实测清单：401/403/404/413/415/429/500/503 与 `WORKFLOW_TIMEOUT`）。所以任务书要求的"409"在这一版应当理解为**重复提交**：由前端禁用按钮 + `state.asking` 拦截实现，**服务端不做幂等键**（本期不做，原因：没有并发写同一资源的场景，加幂等键属于过度设计）。这一条如实登记在附录 B。

### 流程 ⑦ 退出与会话失效（含别的标签页操作时突然 401）

> 涉及路由：任意路由（`#/workbench` … `#/settings`）→ `GET /login`。归档不丢这一事实来自 R7/R8 的数据源（SQLite 归档库）。

| 步 | 动作 | 真实请求 | 用户看到 |
| --- | --- | --- | --- |
| 1 | 点用户按钮 | 无请求（`GET /api/auth/me` 的数据已在内存） | 弹出层显示：登录账号 / 显示名 / 会话到期，最下面是"退出登录"（现有元素 `#user-btn`、`#user-popover`、`#logout`） |
| 2 | 点"退出登录" | `POST /api/auth/logout` | 按钮加载态；`#logout-state` 给 `role="status"` 的进度文字；成功后跳 `/login` 并**清空内存里的用户信息**（现有实现"只以服务端回答为准"，`app/web/app.js:399-407`） |
| 3 | 退出失败（5xx/网络） | — | 就地错误："退出没有成功，请重试"；**不要**假装退出（不跳转、不清本地状态）—— 假退出会让下一个人以为自己是上一个账号 |
| 4 | **别的标签页里会话失效** | 任意受保护请求 → 401 `UNAUTHORIZED` | 当前标签页显示 S5 横幅"登录状态已失效…"，**停掉所有轮询**，跳 `/login` 带 `next`；`session.lost` 标记防止连环跳（现有机制 `app/web/app.js:406`） |
| 5 | 会话到期时间 | `GET /api/auth/me` 的 `session_expires_at`；`GET /api/auth/sessions` 的 `created_at/last_seen_at/expires_at/current` | 设置页与用户弹层都显示到期时间；**到期前不主动弹窗**（没有"续期"接口，弹了也做不了事），到期那一刻由第 4 步处理 |
| 6 | 改密码（本期只在设置页说明，不做表单） | `POST /api/auth/password` 需要 `current_password` | 设置页必须写明："改密码会让该账号的**全部会话**失效，并为当前设备重新签发" —— 否则用户会以为"我改完密码其他设备还开着" |

**实测依据**：`POST /api/auth/logout`、`POST /api/auth/password`（需 `current_password`，成功后 `delete_user_sessions(record.id)` 再为当前设备重签）、`GET /api/auth/sessions` 返回 `SessionData{created_at,last_seen_at,expires_at,current}`；`app/web/app.js:325-328`（401 判定：`res.status === 401 || body.error.code === "UNAUTHORIZED"`）。

## 4 交互动效清单（每条都写信息含义）

规矩：**动效必须携带信息**。没有信息含义的动效（入场淡入、卡片悬停放大、图标旋转装饰）一律不做。

| # | 动效 | 信息含义 | 时长/曲线 | 受 `prefers-reduced-motion` 影响 |
| --- | --- | --- | --- | --- |
| M1 | 按钮 → 加载态（文字换成"上传中…"，图标换成静态进度环） | "你的请求已经发出，现在不要重复点" | 立即（≤80ms） | 否（这是状态切换，不是装饰） |
| M2 | 错误条出现 | "刚才那一步失败了，看这里的原因" | 120ms 高度展开 | **是** → 直接出现不展开 |
| M3 | 阶段圆点：等待(空心灰) → 进行中(实心+呼吸环) → 完成(实心对勾) | "六步走到了哪一步"。呼吸环表示**当前正在跑**，且必须同时有文字"进行中" | 呼吸环 1.6s 循环 | **是** → 呼吸环去掉，只保留实心表示"进行中" |
| M4 | 轮询期间数值更新（耗时数字） | "时间在走，任务还活着" | 每秒跳一次，无过渡动画 | 否 |
| M5 | 上传进度条 | **只在浏览器真的给了 `fetch` 上传进度事件时才出现**，表示"字节真的在传" | 跟随真实进度 | 否 |
| M6 | 骨架屏（灰块） | "这块内容在加载，而且它将来会有多大" | 静态，**不做闪烁动画** | 不适用（本就没有动画） |
| M7 | 会话失效横幅滑入 | "你被登出了，这不是页面崩溃" | 200ms 下移 | **是** → 直接出现 |
| M8 | 焦点环变化（`:focus-visible`） | "键盘焦点现在在这里" | 立即 | 否（无障碍必需） |
| M9 | 报告段落 `cites` 徽章悬停 | "这段数字的出处是 T1" | tooltip 200ms 延迟 | **是** → 立即显示 |

**明确不做**（写进清单是为了后面的人不再提）：卡片入场动画、数字滚动计数（count-up）、图表逐条绘制动画、加载时的品牌 logo 动画、按钮悬停位移、以及任何"看起来在动但不知道在动什么"的效果。理由：这是一个"每个数字都要能核对"的产品，动效一旦抢注意力，就会让人怀疑数字是不是也在被"演"出来。

## 7 阶段状态渲染规范（实测结论）

> 本章只有结论与规范；证据（逐字段出处、原始 JSON、真实运行片段、对账清单）在 `.tmp/ux/stage-truth.md`。
> 本章的每个数字都来自一次真实运行（隔离库、端口 8142、工作流 `08652622164b4adda8858448ce492594`），不是推断。

### 7.1 后端真实可观测面（一句话版）

`GET /api/workflows/{id}` 真实返回 **13 个字段**：`workflow_id` / `dataset_id` / `question` / `status` / `step` / `step_index` / `total_steps` / `tasks[]` / `charts[]` / `error` / `created_at` / `finished_at` / `has_report`（响应模型 `app/schemas_workflow.py:336-361`，字段清单与一次真实抓包的完整响应体逐字核对过）。

**不返回**：`started_at`（`app/schemas_workflow.py:281`）、`heartbeat_at`（`app/schemas_workflow.py:283`）。这两个字段只存在于内存态 `WorkflowState`，而运行态整体是**纯内存**的（`app/core/registry.py:37` `_workflows: dict[str, WorkflowState] = {}`，无落盘），只有终态才归档进 SQLite，且归档表里**没有阶段信息**。

### 7.2 阶段语义（照这个用，不要另立解释）

| 字段 | 语义 | 允许怎么用 | 禁止怎么用 |
| --- | --- | --- | --- |
| `step` | 此刻正在做哪一步；6 个阶段名 + 终态 `done`（`app/schemas_workflow.py:91-99`） | 高亮当前阶段；查中文文案 | 禁止用它推算"还剩多久" |
| `step_index` | **= 已完成的阶段数**（`app/agents/orchestrator.py:434` 写 `state.step_index = _STEPS.index(step)`，而这个赋值发生在**进入**某阶段时，所以进 `charting` 时前三个阶段确实已走完、值是 **3**）。同时它也是当前阶段在 `_STEPS` 里的下标：当前阶段本身就是 `_STEPS[step_index]` | 显示"（3/6）"；给已走过的阶段上色（`i < step_index`）；**它就是完成比例，直接除以 `total_steps`** | 禁止拿它"乘以单阶段平均耗时"去推算剩余时间（各阶段耗时差两个数量级，见 `docs/limitations.md` N7） |
| `total_steps` | 固定 6 | 分母 | — |
| `tasks[].status` | 每个任务的真实状态 | 任务清单 | 禁止把"任务成功数"当成"阶段完成数" |
| `charts[]` | 已生成的图表（终态才有内容） | 取 `url` 渲染 | 禁止在 `charts` 为空时先摆图位再等它出现（会闪） |
| `created_at` / `finished_at` | 工作流级起止时间，UTC 带 `Z` | 算总耗时 | 禁止拿它拆成阶段耗时 |

**实测样例（真实响应原文）**：`t=16ms → status=PROFILING, step=profiling, step_index=0, tasks=[]`；`t=85ms → status=CHARTING, step=charting, step_index=3, tasks=[T1 SUCCESS, T2 SUCCESS]`（**此刻已完成的阶段 = profiling / planning / execution 三个**，`step_index=3` 正好等于这个数；`T1/T2` 是**工具任务**，不是阶段）；`t=327ms → status=SUCCESS, step=done, step_index=6, finished_at 有值`。

### 7.3 两条渲染路径的规范

**情况一：后端只有总状态（即今天的样子）—— 必须这样渲染**

1. 阶段列表**只能**高亮 `i < step_index` 为已完成、`i === step_index` 为进行中，其余为等待。**不许**按时间自行推进、**不许**给"进行中"的阶段画百分比。
2. 进度数字**只能**来自 `step_index` / `total_steps`。`step` 认不出来时（后端新增阶段）按 `app/web/app.js:2007-2011` 的既有约定：终态当全部走完、否则当还没开始，**绝不猜中间值**。
3. **禁止显示"阶段耗时"**（定案 D6）。今天没有任何字段能支撑它，写了就是编造。
4. **禁止显示"排队等待了 N 秒"**。`started_at` 未暴露。
5. 允许显示"已用时"（`created_at` → `finished_at` / 现在），但**必须挡住负数**：现有 `app/web/app.js:239-249` 的 `formatSeconds()` 没有负数分支，浏览器时钟落后时会显示"已用时 -12.3 秒"。修法二选一：`seconds < 0` 时显示"—"，或改用 `max(0, seconds)`。
6. 阶段名与顺序必须与后端的 `WorkflowStep` 逐字一致（`app/web/app.js:62` 的 `STEP_ORDER` ↔ `app/schemas_workflow.py:91-99`）。目前是两边各抄一份，**没有断言**；后端加阶段时前端会静默退回起点。
7. 归档详情页（`app/web/app.js:2614` `openHistoryDetail()`）只有键值表：那里**不能**出现阶段时间线（归档表里没有阶段信息）。

**情况二：后端补齐阶段事件后 —— 才可以这样渲染**

只有 §7.5 的 ③ 落地后（`stage_events: [{step, at}]` 随状态接口返回），才允许：

1. 画真实阶段时间线与每阶段耗时，且**单位与来源都标注**（"取自服务端 stage_events"）；
2. 显示"最近一次进展距今 N 秒"（用服务端算的 `idle_seconds`，**不要用客户端时钟**去减服务端时间戳）；
3. 在归档详情里回看当时的阶段序列（需归档表同步加列）。

### 7.4 全局红线：不许伪造 Agent 进度

- 不许用 `setTimeout` / `setInterval` 推进阶段（唯一的定时器只能是轮询 `app/web/app.js:2090`）；
- 不许写死秒数、不许写死百分比、不许摆"预计剩余时间"；
- 不许在界面上出现任何无法指向 `app/schemas_workflow.py` 里某个字段的阶段状态；
- 本条与任务书 7.3「必须来自真实工作流事件」是同一条规则。

### 7.5 后端改造需求（一句话摘要 + 优先级）

**一句话**：只需在 `WorkflowState` 上加一个阶段事件列表（在 `app/agents/orchestrator.py:433-434` 唯一改动 `state.step` 的地方 append 一条 `{step, at}`）并随状态接口返回，再顺手暴露 `started_at` 与派生值 `idle_seconds`，前端就能如实展示阶段耗时与"是否卡住"；**今天这三样都没有，所以这三样都不许画**。

| 优先 | 需求 | 向后兼容方式 |
| --- | --- | --- |
| 高 | 状态接口加 `stage_events: [{step, at}]` | 纯新增字段，老客户端忽略 |
| 高 | 状态接口加 `idle_seconds: float \| None`（服务端现算，避免客户端时钟参与） | 纯新增 |
| 中 | 状态接口加 `started_at` | 纯新增 |
| 低 | 归档表加阶段快照列 | 需 `schema_version` 迁移 |

**不推荐**：把轮询间隔从 1000 ms 降到 100 ms。实测工作流 0.3 秒跑完，加密轮询只会多打几次接口、多看到一两帧，缺的是数据不是采样率。
